# 延期的设备验证审批设计说明

## 状态

本文件记录已经延期、当前不启用的“设备验证任务化”方案。它保留未来安全增强所需的边界，不是当前 Android 运行路径、产品验收依据或审批中心数据来源。

当前依据是[我的页审批、设备管理与用户资料设计](../specs/2026-09-02-my-tab-approval-device-profile-design.md)：

- 短信验证码校验成功后，首次和后续 Android 设备都创建或恢复为 `ACTIVE`，立即可读写；本轮不创建设备授权请求。
- Android“我的”页的审批中心只展示任务审批。任务列表、四象限和日程的“更多”菜单不提供任务审批入口。
- 设备管理只能撤销当前账号下的其他设备，当前设备不可撤销；每次撤销都必须经过客户端二次确认，并使被撤销设备的移动会话失效。
- 历史兼容迁移把未撤销的 `PENDING` 设备转为 `ACTIVE`，使未完成的设备授权请求过期，保留 `REVOKED` 设备、会话撤销状态和审计历史。

## 未来方案边界

如果以后重新启用设备验证审批，应继续使用独立的 `DeviceAuthorizationRequest` 和设备挑战/签名字段，不把设备请求写入 `Task` 或伪装成普通 `TaskApprovalRequest`。重新启用前需要另行确认：

1. 设备请求的状态机、过期和幂等规则；
2. 候选设备与审批设备的账号、Workspace 和 ACTIVE 状态校验；
3. 安全短码、签名挑战、撤销会话和审计记录的完整链路；
4. Android UI、API、迁移和跨层契约测试；
5. 与当前“短信验证即可信”策略的兼容迁移及回滚边界。

在上述设计、测试和发布门禁完成前，任何文档、fixture 或客户端都不得假设新增设备需要另一位成员批准，也不得把设备授权请求显示为任务审批。
