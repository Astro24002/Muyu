# Email OTP Authentication with Aliyun DirectMail

## Status

Approved direction: replace SMS authentication with email verification codes;
do not add passwords. This is a new Workspace/database rollout, so the old
phone-auth schema does not need a data compatibility migration.

## Goals

- Use a normalized email address as the login and registration identifier.
- Keep the existing device identity, two-person workspace approval, recovery,
  Web QR login, and session rules unchanged.
- Send production verification mail through Aliyun DirectMail
  `SingleSendMail`.
- Keep local development and automated tests deterministic with a fake mail
  provider.
- Retain an optional phone field as unverified profile information only.

## Non-goals

- No password login, password reset, or password-derived credential.
- No phone ownership verification, phone login, phone-based invitation, or
  phone-based recovery in this release.
- No iOS client work.
- No migration of data from the previous phone/P2P system.

## Identity and data model

`users.id` remains the UUID primary key and internal stable identifier.
`users.email` becomes a required, normalized, unique login identifier. The
normalization rule is trim surrounding whitespace and lowercase the full
address before lookup or persistence; the application does not use the raw
input as an identity key.

`users.phone` becomes nullable, non-unique profile data. The server does not
claim that this value is verified, and no authentication or authorization path
uses it. The profile response may expose the value as nullable, and an
authenticated profile update may set or clear it with basic length validation.

Workspace invitations and membership matching use email. Phone change request
records are removed from the authoritative schema and replaced by the normal
profile update behavior; changing an unverified phone does not require a
second-party approval.

The SMS challenge table becomes an email OTP challenge table with an email
subject, keyed digest, attempt counter, request IP digest, expiry, consumption
timestamp, and creation timestamp. It must not store the plaintext code.

## API contract

Replace the mobile routes with:

- `POST /api/v1/auth/email/send` with `{ "email": "..." }`;
- `POST /api/v1/auth/email/verify` with `{ "email": "...", "code": "...", "device": ... }`;
- `POST /api/v1/auth/mobile/refresh`, `POST /api/v1/auth/mobile/logout`, and
  `GET /api/v1/me` remain otherwise compatible, with `user.email` and nullable
  `user.phone` in the response;
- `PATCH /api/v1/me` accepts optional `display_name` and nullable `phone`.

Email inputs are validated as email addresses and normalized before rate
limiting, challenge lookup, and user lookup. The send response never reveals
whether the address already has an account.

Invite requests accept `email`, and accepting an invite matches the normalized
email. Recovery and device-loss flows continue to identify users by UUID and
workspace membership; they do not introduce a phone fallback.

## Delivery boundary

Introduce an `OtpDeliveryProvider` protocol with a fake implementation and an
Aliyun implementation. The Aliyun adapter uses the official DirectMail SDK or
its documented RPC client for `SingleSendMail`, with:

- `ALIBABA_CLOUD_ACCESS_KEY_ID` and `ALIBABA_CLOUD_ACCESS_KEY_SECRET` supplied
  only by the server secret store;
- `ALIYUN_DM_ACCOUNT_NAME` set to a verified sender address under the sending
  domain;
- `ALIYUN_DM_REGION_ID` defaulting to `cn-hangzhou`;
- a fixed verification-mail subject and text/HTML body generated by the API;
- no OTP, recipient address, AccessKey, or provider response body in logs.

The production RAM principal receives only the `dm:SingleSendMail` permission.
The sending domain/address must be verified in Aliyun DirectMail before
deployment; SPF, DKIM, and DMARC records are deployment prerequisites.

Provider failures return a generic 503 delivery error and do not persist an
OTP challenge. Provider configuration is rejected at startup when production
mode lacks required credentials or sender settings.

## Security and limits

- Six ASCII digits, five-minute expiry, one successful use.
- Maximum five verification attempts per challenge.
- Separate per-email and per-IP send windows; use a keyed email digest in
  advisory-lock/rate-limit keys where appropriate.
- Generic send and verification errors that do not disclose account existence.
- Access/refresh sessions remain opaque, revocable, device-bound, and stored
  with only digests as before.
- Web QR login and the 18-hour Web session maximum are unchanged.

## Client behavior

Rename the Android login surface and repository methods from phone/SMS to
email. The UI validates an email address, requests a code, and submits the
device public key with verification. Error, retry, and session restoration
behavior remain unchanged. The Web client still authenticates only through QR
approval by an active Android device.

## Deployment and tests

Local Compose uses a fake email provider and a deterministic test code. The
production environment template documents Aliyun variables without values.
Tests cover normalization, duplicate email rejection, one-time/expired/wrong
codes, rate limits, provider failure rollback, optional unverified phone
profile data, invite matching, and the end-to-end Android/Web protocol. Run
backend PostgreSQL tests, Flutter format/analyze/tests, deployment config
checks, and Android/Web release builds.

## Rollout

Provision a new empty PostgreSQL database, apply the new Alembic head, verify
the Aliyun sender domain and a real recipient mailbox, then deploy the API and
Web bundle. Do not point this release at the previous phone/P2P data volume.
