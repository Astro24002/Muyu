# 开发路线

## 当前路线：云端协调架构（2026-08-24）

后续实现以 [云端协调双人协作架构设计](./superpowers/specs/2026-08-24-cloud-coordinated-collaboration-design.md) 为架构依据，并以 [移除任务参与人模型设计](./superpowers/specs/2026-09-01-remove-task-participants-design.md) 作为当前任务模型、读取范围、写入审批、Android 概览、迁移和缓存规则的权威：PostgreSQL 保存明文协作事实，FastAPI 以 REST 增量同步和通知型 WebSocket 协调 Android 与 Web。首版交付 Android APK/AAB 与 Web 静态构建；iOS 仅保留协议扩展空间，不进入当前构建、发布或验收。

新系统从空 Workspace 与新 PostgreSQL 模型开始，不迁移旧数据，也不保留 P2P、固定密码后端或旧 API 兼容路径。旧 P2P 运行时和旧后端代码将在后续经审阅的实施计划中受控删除。详细实施顺序尚未创建，必须在规格复核后另行编写。

## 历史路线（仅作记录）

## 发布分层

本项目不把所有功能一次性视为同一个 MVP：

- `MVP-Core`：Phase 0-3，先跑通两人任务闭环和完整行为记录；
- `MVP-Extended`：Phase 4-7，补充冲突、事件、循环任务、评论和首页；
- `Post-MVP`：Phase 8-9，在真实使用数据基础上做统计和反拖延优化。

只有 `MVP-Core` 完成后，才进入下一层。任何新增功能都不能阻塞核心闭环。

## Phase 0：工程基础

目标：跑通完整部署链路。

- Git 仓库；
- Flutter Android/Web 工程；
- Go API；
- PostgreSQL；
- Docker Compose；
- Caddy；
- Migration；
- HTTPS；
- CI/CD 基础流程。

验收：

- Android 能登录 API；
- Web 能登录 API；
- API 能连接 PostgreSQL；
- 数据库能完成初始化和迁移；
- ECS 能通过 HTTPS 访问。

## Phase 1：双人系统

- 初始化两名固定用户；
- 手机号和统一密码登录；
- Access/Refresh Token；
- 昵称修改；
- 角色修改；
- 固定头像；
- 获取双方用户信息；
- 基础会话撤销。

验收：

- 两台设备可以分别以两个固定用户登录；
- 双方看到统一数据；
- 昵称和角色修改后双方可刷新看到；
- 头像不可修改。

## Phase 2：Task 和子任务

- 创建、查看、编辑、取消任务；
- 每项任务只有一个 `current_handler_id`；
- 同一 Workspace 的两位 ACTIVE 成员可读取全部未删除任务和子任务；
- 当前负责人可直接写入，另一位成员的受保护写入继续走对方审批；
- 用户独立任务排序；
- 转交负责人；
- 开始、完成、重开；
- 一层子任务；
- 计划开始时间；
- 截止时间；
- 预计耗时。

验收：

```text
创建
  -> 确定当前负责人（默认是创建者）
  -> 开始
  -> 转交
  -> 完成
  -> 双方刷新看到同一状态；非负责人写入须经对方审批
```

## Phase 3：延期和阻塞

- DelayRecord；
- 延期原因必填；
- `OTHER` 补充说明；
- 延期次数和累计延期时间；
- WAITING 状态；
- 阻塞原因必填；
- 解除阻塞后的继续处理人；
- 状态历史；
- 负责人历史；
- 统一 ActivityEvent。

验收：

- 一个任务延期三次后可以查看三次完整记录；
- 每次延期保留原截止时间和新截止时间；
- 进入阻塞时必须说明原因和后续负责人；
- 解除阻塞后自动恢复到正确处理人。

## Phase 4：状态冲突

- `status_version`；
- 过期版本返回 409；
- 创建冲突记录；
- 冲突专区；
- 双方确认最终状态；
- 冲突解决事件；
- 旧冲突被新状态提交替代时标记 `SUPERSEDED`。

验收：

- 两台设备同时修改同一任务状态时不发生静默覆盖；
- 冲突不影响其他任务和普通字段；
- 双方确认相同结果后任务才合并；
- 所有状态尝试和解决过程可审计。

## Phase 5：重要事件

- 一次性事件；
- 日期型事件；
- 具体时间事件；
- 年度纪念日；
- 北京时间倒计时；
- 时间轴；
- 软删除。

验收：

- 可以创建婚礼、旅行、预约和纪念日；
- 正确显示还有多少天或已过去多少天；
- 纪念日自动计算下一次发生日期。

## Phase 6：循环任务

- 每日；
- 每周；
- 每月；
- 暂停和恢复；
- Task Instance；
- 幂等生成；
- 错过周期不补历史任务；
- 月末日期处理。

验收：

```text
RecurringTask
    -> 到期
    -> Task Instance
    -> 完成
    -> 计算下一次 occurrence
```

## Phase 7：协作和首页

- 评论；
- 任务时间线；
- 首页 `/api/home`；
- 当前处理任务；
- 用户自定义顺序；
- 阻塞任务；
- 到期提醒；
- 重要事件倒计时；
- 未处理冲突数量。
- Android“我的”账户概览：统计当前用户负责的全部未删除父任务和子任务，并汇总完成、未完成和延期数据；匹配对象头像打开对方的同口径概览。

首页默认展示用户排序中的前 5 条开放任务，不显示系统优先级。

## Phase 8：数据分析

第一批指标：

- 到期任务数；
- 完成任务数；
- 延期任务数；
- 延期次数；
- 累计延期时间；
- 平均延期时间；
- 中位延期时间；
- 重复拖延率；
- 平均启动延迟；
- 共同任务拖延率。

第一版统计实时计算，不保存汇总缓存。

Android“我的”中的账户概览是从现有 Workspace snapshot 派生的紧凑视图，不属于独立的数据分析子系统；不新增 analytics API、统计表或统计缓存。

## Phase 9：反拖延优化

根据真实使用数据优化：

- 首页展示数量；
- 任务拆分体验；
- 阻塞原因分类；
- 重复延期提示；
- 等待对方识别；
- 时间段行为分析；
- 自动拆分建议。

AI 放在这一阶段，不进入 MVP。

## 最终验收原则

每个产品功能都应回答：

1. 是否帮助用户更快开始？
2. 是否帮助两个人更好协作？
3. 是否减少任务过载？
4. 是否记录真实行为？
5. 是否能够发现拖延模式？

如果不能回答这些问题，不因为“看起来很酷”而进入 MVP。
