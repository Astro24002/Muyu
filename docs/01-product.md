# 双人协作行动管理系统

## 1. 产品定义

这是一个只服务于两个人的私人行动记录与提醒应用。

它不追求成为通用 Todo、团队协作平台或复杂的数据分析系统，而是解决两个人日常生活中的几个具体问题：

- 现在正在处理什么；
- 下一步由谁继续；
- 什么事情被阻塞了，为什么；
- 截止时间是否发生过延期；
- 重要日期什么时候到来；
- 任务和子任务经历过哪些变化。

产品核心价值：

> 让两个人更容易开始行动，也让事情的真实过程不会丢失。

## 2. 产品边界

这是一个小而精的私人应用程序。

系统只服务于固定的两名用户，不提供以下平台化能力：

- 注册和邀请其他用户；
- Workspace、Team、Organization；
- 多租户；
- RBAC 和复杂权限；
- 公开分享；
- 社交关系；
- 排行榜、积分和惩罚；
- AI 自动规划；
- 复杂实时通信。

所有设计优先考虑：少配置、少页面、少打扰、低维护成本。

## 3. 用户模型

系统固定只有两名用户：

| 用户 | 登录手机号 | 默认角色 |
| --- | --- | --- |
| 用户 A | `15028180169` | 男方 |
| 用户 B | `15068128726` | 女方 |

登录使用手机号和同一套固定密码。手机号是固定用户 ID，头像固定，昵称和角色允许用户修改。

角色仅用于展示，所有业务逻辑始终使用 `user_id`。两名已登录用户默认拥有这个私人空间内的完整读写能力，不做任务级权限管理。

## 4. 设计原则

### 4.1 记录事实，不替用户决策

系统不保存或计算：

- 业务优先级；
- 紧急程度；
- 重要程度；
- 系统评分；
- 双方排名；
- 自动推荐顺序。

用户可以为自己维护任务展示顺序，但这个顺序只是个人展示偏好，不是系统判断出的优先级。

### 4.2 一次只面对少量事情

首页不展示全部任务，也不强调“还有多少未完成”。

首页只展示：

- 当前用户正在处理的任务；
- 当前用户排序靠前的少量开放任务；
- 阻塞任务；
- 临近或已经到期的任务；
- 重要日期和纪念日；
- 未处理的状态冲突。

完整任务列表始终可进入，但不作为首页默认内容。

### 4.3 每个任务都要能说明下一步

任务应当足够具体，能够直接开始。

过大的目标可以拆成一层子任务，例如：

```text
准备婚礼
├── 确定酒店
├── 联系婚庆
└── 整理宾客名单
```

系统不自动拆分任务，只提供清晰的拆分记录。

### 4.4 不隐藏拖延，但不惩罚拖延

延期、阻塞和重复延期都是事实记录，不是失败标记。

系统可以提醒：

> 这个任务已经延期 3 次。

但不进行扣分、排名、羞辱或双方比较。记录的目的只是帮助双方发现任务过大、目标不清晰或等待关系不明确。

## 5. 核心对象

### 5.1 Task

Task 表示需要采取实际行动的事情。

支持：

- 标题和描述；
- 一名或两名参与人；
- 当前实际处理人；
- 计划开始时间；
- 截止时间；
- 预计耗时；
- 开始、完成、取消和重新打开；
- 转交负责人；
- 进入阻塞和解除阻塞；
- 延期；
- 评论；
- 一层子任务。

### 5.2 Subtask

子任务仍然使用 Task 模型，通过 `parent_task_id` 关联父任务。

第一版只支持一层子任务。父任务和子任务状态相互独立，完成子任务不会自动完成父任务。

父任务即使仍有未完成子任务也可以完成，但界面必须提示确认，并记录该行为。

### 5.3 Event

Event 表示具有明确时间节点的事情，重点是“什么时候发生”，而不是“是否完成”。

支持：

- 重要日期；
- 婚礼、旅行、搬家；
- 生日、预约；
- 一次性事件；
- 年度纪念日。

倒计时根据事件日期或时间实时计算，不保存剩余天数。

### 5.4 RecurringTask

RecurringTask 表示需要反复执行的生活任务，例如喂猫、打扫卫生和缴费。

第一版只支持每日、每周和每月。系统最多保留一个未完成实例，错过多个周期时不补充历史积压任务。

## 6. 任务协作模型

### 6.1 参与人和当前负责人分开

- `assignees`：参与任务的用户，可为一人或两人；
- `current_handler_id`：当前实际处理人，MVP 始终只有一人。

两个人经常交换负责人，因此转交是正常操作，不是异常流程。

### 6.2 状态

```text
TODO
IN_PROGRESS
WAITING
DONE
CANCELLED
```

状态含义：

- `TODO`：已创建但尚未开始；
- `IN_PROGRESS`：当前有人正在处理；
- `WAITING`：被外部条件阻塞；
- `DONE`：已完成；
- `CANCELLED`：不再需要执行。

允许从 `DONE` 或 `CANCELLED` 恢复，历史记录不会丢失。

### 6.3 阻塞

进入 `WAITING` 时必须填写：

- 阻塞原因；
- 解除阻塞后继续处理的用户。

可以额外说明正在等待哪一位用户。

解除阻塞后，任务恢复为 `IN_PROGRESS`，并由预先记录的用户继续处理。

## 7. 延期记录

延期原因必须填写。每次延期都生成一条不可修改的记录，不能直接覆盖历史。

延期记录包含：

- 原截止时间；
- 新截止时间；
- 延期用户；
- 延期原因；
- 延期时长；
- 补充说明；
- 创建时间。

第一版原因枚举：

```text
NO_TIME
TOO_LARGE
NOT_WILLING
FORGOT
WAITING_PARTNER
INTERRUPTED
OTHER
```

选择 `OTHER` 时必须填写补充说明。

## 8. 状态冲突

冲突只针对同一个任务的并发状态修改。

冲突不会成为任务状态，也不会锁住任务或影响其他任务。双方可以通过其他沟通方式协商，再回到应用中确认最终结果。

处理方式：

1. 服务端发现状态版本过期；
2. 保留已经成功写入的状态；
3. 创建冲突记录；
4. 双方在冲突专区看到双方提交的状态；
5. 双方确认相同的最终状态；
6. 服务端合并并关闭冲突。

如果期间产生了更新的状态，旧冲突标记为 `SUPERSEDED`，不阻塞后续操作。

## 9. 活动记录

任务和子任务的所有变更都需要记录：

- 创建；
- 修改；
- 分配参与人；
- 转交负责人；
- 开始；
- 进入阻塞；
- 解除阻塞；
- 延期；
- 完成；
- 取消和恢复；
- 创建子任务；
- 评论；
- 冲突产生和解决。

活动记录只允许新增，不允许修改或删除。它用于任务时间线、延期回顾和冲突审计。

## 10. 首页内容

首页默认展示：

1. 当前用户正在处理的任务；
2. 按当前用户顺序排列的前 5 条开放任务；
3. 阻塞任务及阻塞原因；
4. 已到期和即将到期提醒；
5. 重要事件和纪念日倒计时；
6. 未处理的状态冲突数量；
7. 最近活动。

用户排序独立保存，用户 A 的排序不会影响用户 B。时间提醒按时间排列，但不代表业务优先级。

## 11. 产品范围

### 核心闭环

第一阶段只要求跑通：

```text
两人初始化
  -> 登录
  -> 创建任务
  -> 分配参与人
  -> 指定当前负责人
  -> 开始
  -> 转交或阻塞
  -> 延期并记录原因
  -> 完成
  -> 双方看到一致状态
```

### 核心闭环之后

- 子任务；
- 评论和任务时间线；
- 重要事件和纪念日；
- 循环任务；
- 首页提醒；
- 状态冲突专区；
- 基础延期统计。

### 明确不做

- 多租户和组织体系；
- 复杂权限；
- 社交和公开分享；
- WebSocket、Push 和消息队列；
- AI 自动规划；
- 自动任务排序；
- 排行榜、积分和惩罚机制。

## 12. 产品验收原则

每项功能都应回答：

1. 是否让用户更容易开始？
2. 是否让两个人更容易协作？
3. 是否减少一次看到的任务数量？
4. 是否保留真实行为记录？
5. 是否避免引入不必要的复杂度？

如果一个功能不能改善上述至少一项，就不进入这个私人应用的核心版本。
