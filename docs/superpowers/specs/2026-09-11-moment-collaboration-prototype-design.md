# Muyu「此刻」协作链浏览器原型设计

> 2026-09-17 适用范围更新：最新目标为 [Muyu 设计交付 v1.0](../../../Muyu-Codex-Design-and-Implementation.md)，工程适配见 [v1 契约](./2026-09-16-muyu-v1-contract-and-delivery-design.md)。本文旧导航、品牌/头像栏、首页分组或原型交付范围如有冲突，以新基线为准：事项/记账/打卡/我的，事项标题内切三视图，此刻互斥三段；纪念日在打卡内。未冲突的视觉令牌、可访问性及历史验证记录保留；原型数据和验收不代表生产实现。本次不重做或发布原型。

## 1. 文档状态与目的

本文冻结 Muyu 下一轮浏览器交互原型的产品基线，验证一条双人任务在「此刻」首页、任务详情、交接、验收和完成之间如何连续流转。

本文的核心结论是：

> 一个任务，一个负责人；协作过程中，明确下一棒。

> 此刻：现在轮到谁？下一步是什么？

本轮交付是可操作的浏览器原型，不是生产功能施工。原型可以使用本地模拟数据和内存状态演示双方视角，但不代表后端接口、数据库迁移、权限校验、持久化、同步协议或 Android 客户端已经完成。后续生产实施仍需另行编写规格和施工计划。

本文不授权修改业务代码。浏览器原型预计由本地开发服务器在 `5175` 端口提供预览。

## 2. 与既有规格的关系

任务领域继续沿用现有约束：

- 一个 Workspace 最多两名 ACTIVE 成员；
- 一个任务始终只有一个 `current_handler_id`；
- 两位成员都能读取同一 Workspace 内的未删除任务；
- 状态、请求结果和关键协作内容需要保留活动历史；
- 任务负责人不能绕过另一位成员的验收直接完成任务。

本文只冻结新的产品入口、首页投影和协作链原型。它在 UI 投影上覆盖此前“今天页只展示当前用户任务、不展示对方一般任务”的设计：默认工作台改为「清单 → 此刻」，并同时显示当前用户和对方正在推进的事情。

底层状态、单负责人和双人验收规则不因原型而改变。与本文无关的认证、设备、分类、象限、同步和冲突规则仍以既有规格为准。

## 3. 产品边界

### 3.1 本轮冻结

- 「清单」底部导航的默认内容为「此刻」，不再称为“近期任务”；
- 此刻首页固定使用“卡住的事情、我在推进、对方在推进”三个主体分组；
- 顶部提供“需要我处理、等对方、本周到期”三个问题入口；
- 任务详情以“下一步”为主要行动信息；
- 负责人交接在对方接受前不改变负责人；
- 负责人提交验收后，只有另一位成员可以通过或退回；
- 通过后任务才进入已完成，退回后回到进行中；
- 交接说明、验收内容、拒绝、退回和撤回结果作为历史事实保留；
- “查看全部事情”提供完整任务发现路径。

### 3.2 本轮不做

- 不增加第三位成员、多人负责人、参与人或“我们”负责人；
- 不引入项目、Sprint、自定义工作流、聊天、积分或工作量统计；
- 不新增独立的“下一步”字段或编辑器；
- 不扩展附件、文件预览或版本管理；
- 不冻结子任务在此刻首页中的聚合、缩进、计数或父子联动细节；
- 不冻结首页大数据量下的截断数量、分页和折叠策略；
- 不用原型替代生产权限、事务、幂等、同步和可访问性验收。

## 4. 任务状态与协作请求分离

### 4.1 任务状态

用户界面继续只使用以下六个中文状态：

| 内部状态 | 中文展示 |
| --- | --- |
| `TODO` | 待进行 |
| `IN_PROGRESS` | 进行中 |
| `BLOCKED` | 阻塞中 |
| `REVIEW` | 待验收 |
| `DONE` | 已完成 |
| `CANCELLED` | 已取消 |

状态描述任务当前所处的生命周期阶段，不描述某一位用户当前收到的请求。

### 4.2 协作请求

产品层的协作请求包括：

- 验收请求；
- 交接请求；
- 其他需要另一位成员决定的审批请求。

请求有独立生命周期：发起后进入等待，随后被接受或通过、拒绝或退回、撤回，或者因既有领域规则失效。任务状态和请求状态不能混为一个枚举。

例如：

- “待验收”是任务状态；
- “等待 Bokang 验收”是当前协作上下文；
- “等待溪岸接受交接”不是任务状态，交接等待期间任务仍为进行中；
- “等待酒店补充合同”是阻塞事实，不是协作请求。

拒绝、退回和撤回只结束本次请求，不删除请求记录。再次交接或再次提交验收必须创建一条新请求，不能重新打开旧请求。原型只需表达这项产品语义，不在本轮冻结具体后端枚举或字段名。

## 5. 导航与三个问题入口

底部导航保持：

```text
清单   四象限   日程   我的
```

进入「清单」时首先看到「此刻」。此刻不是全部任务列表的一个筛选条件，而是双人协作的默认工作台。

顶部三个入口是三个不同问题，不是互斥筛选，也不能把数字相加理解为任务总数：

| 入口 | 统计对象 | 冻结口径 |
| --- | --- | --- |
| 需要我处理 | 请求 | `approver_id` 为当前用户且仍待处理的协作请求 |
| 等对方 | 请求 | `requester_id` 为当前用户且仍待处理的协作请求 |
| 本周到期 | 任务 | 当前自然周到期、未删除且未结束的任务 |

“未结束”包括待进行、进行中、阻塞中和待验收，不包括已完成和已取消。本周入口是独立时间视角，其中可以同时看到我负责、对方负责、阻塞中或待验收的任务。

前两个数字只统计待处理请求。即使一个阻塞任务的等待对象明确是对方，只要没有一条待处理协作请求，它就不增加“等对方”数量；该任务只留在“卡住的事情”。这条规则避免把任务数和请求数暗中混合。

三个入口在视觉上使用克制的文字和数字，不使用三个高权重状态卡或强 badge，避免制造三个互斥任务集合的错觉。

## 6. 此刻首页投影

### 6.1 固定结构

首页主体固定为：

```text
卡住的事情
我在推进
对方在推进

查看全部事情
```

其中：

- “卡住的事情”包含双方负责的 `BLOCKED` 任务；
- “我在推进”包含当前用户负责的 `TODO` 和 `IN_PROGRESS` 任务；
- “对方在推进”包含另一位成员负责的 `TODO` 和 `IN_PROGRESS` 任务；
- `REVIEW` 不进入上述三个主体分组，只从“需要我处理”或“等对方”的请求入口查看，同时仍可在“全部事情”中找到；
- `DONE` 和 `CANCELLED` 不进入此刻主体，只在“全部事情”等完整视图中出现；
- 已删除任务不出现在此刻或“全部事情”。

### 6.2 首页去重

同一任务在此刻主体中只出现一次。归组优先级是：

```text
BLOCKED → 卡住的事情
否则 TODO / IN_PROGRESS → 按当前负责人进入我或对方
否则 → 不进入此刻主体
```

顶部数字只是入口摘要，不是第二份任务列表，因此任务同时影响一个入口数字和主体中的一行不构成重复。本周到期也是进入后的独立时间视角，不受主体去重限制。

### 6.3 排序及明确取舍

此刻首页首先固定分组顺序，再在组内排序：

```text
卡住的事情
↓
我在推进
↓
对方在推进
```

“我在推进”和“对方在推进”各自按以下顺序排列：

```text
逾期
↓
即将到期
↓
较远截止
↓
无截止时间
```

“卡住的事情”同样先按逾期、即将到期、较远截止和无截止时间排列；截止条件相同时，可以再让阻塞时间更长的任务提前。

相同截止条件下应使用稳定次序，生产实现的最终 tie-breaker 不在本原型中冻结。

这里有一个刻意接受的取舍：固定“我在推进”先于“对方在推进”，意味着对方的逾期任务不一定排在我的正常任务之前。因此，本轮不能宣称首页实现了跨负责人分组的全局“逾期优先”。全局提升的异常只有“阻塞中”；逾期优先只在我和对方各自的组内成立。若未来要让所有逾期任务全局提前，需要新增独立逾期组或改成混合列表，不属于当前基线。

### 6.4 任务行

普通任务行控制为两层信息：

```text
确认菜单                         周六
溪岸 · 进行中 · 婚礼
```

逾期时，右侧时间替换为明确文字，例如“逾期 2d”。阻塞任务允许第三行展示可行动的事实：

```text
确认酒店
溪岸 · 阻塞中 2d04h
等待酒店补充合同
```

任务行不同时堆叠优先级、创建时间、更新时间、评论数、子任务数等详情字段。分类可以作为第二行最后一项；色彩不能替代“阻塞中”“逾期”等文字。

### 6.5 全部事情

“查看全部事情”不是近期窗口，而是完整发现入口。它包含：

- 所有截止时间，包括逾期、未来、本周以外和无截止时间；
- 六种任务状态；
- 双方负责的任务；
- 所有未删除任务。

已删除任务不在此入口。恢复和删除历史的入口不在本轮冻结。父任务和子任务是否作为独立行、如何缩进以及如何计数也不在本轮冻结。

## 7. 任务详情与“下一步”

任务详情的信息层级固定为：

```text
标题与基础元数据
当前情况
下一步
任务描述或协作内容
活动记录
当前用户可执行的动作
```

“下一步”按当前事实和当前查看者生成，不引入独立编辑器，也不编造系统不知道的具体行动：

| 当前事实 | 发起人或负责人看到 | 另一位成员看到 |
| --- | --- | --- |
| 普通进行中 | 继续处理任务 | 由负责人继续处理 |
| 交接请求待处理 | 等待对方接受交接 | 接受或拒绝交接 |
| 待验收 | 等待对方验收 | 确认验收结果 |
| 验收被退回 | 修改后重新提交验收 | 等待负责人修改 |
| 阻塞中 | 展示真实阻塞原因和解除后的动作 | 展示相同阻塞事实 |

如果用户已经在任务描述、阻塞说明或请求内容中写下具体动作，详情可以原样展示；系统不能从“进行中”推测出“继续比较套餐”这类不存在的数据。普通进行中没有更具体事实时，使用“继续处理任务”。

同一个任务的事实相同，但操作按钮随查看者权限变化。原型不能让请求发起人看到处理自己请求的“接受、通过、退回”按钮。

## 8. 六屏连续故事

原型使用同一条真实任务贯穿全部页面，不制作六张互不相干的静态图。人物和责任顺序固定为：

```text
Bokang 创建并推进
        ↓
Bokang 发起交接
        ↓
溪岸接受并继续推进
        ↓
溪岸提交验收
        ↓
Bokang 通过或退回
```

任务标题为“确认婚礼酒店”，分类为“婚礼”。原型可用同一任务的模拟数据切换 Bokang 与溪岸视角。

### 8.1 屏一：此刻首页

起始事实：负责人是 Bokang，状态是进行中，尚无待处理协作请求。

- Bokang 视角：任务位于“我在推进”；两个请求入口都不因本任务增加数字。
- 溪岸视角：任务位于“Bokang 在推进”；两个请求入口都不因本任务增加数字。
- 双方任务行展示同一个负责人、状态、分类和截止时间。
- 打开任务行进入同一任务详情，不生成新的任务副本。

该屏同时用另一条固定示例任务验证“卡住的事情”：如果其阻塞说明是“等待酒店补充合同”，它只进入阻塞区；仅凭“等待”文字不能增加“等对方”。

### 8.2 屏二：进行中详情

起始事实仍为 Bokang 负责、进行中。

- Bokang 看到“下一步：继续处理任务”，并能发起交接或提交验收；
- 溪岸看到负责人是 Bokang 和相同活动事实，但没有代替 Bokang 发起负责人交接或提交验收的主按钮；
- 页面展示截止时间、分类和描述，但不把所有元数据压进首页任务行；
- “活动”至少能说明 Bokang 创建任务并开始处理。

### 8.3 屏三：Bokang 发起交接

Bokang 选择交给溪岸并填写交接说明，例如“酒店后续需要持续沟通，请继续跟进合同”。提交后的事实是：

- 交接请求进入待处理；
- 任务负责人仍是 Bokang；
- 任务状态仍是进行中；
- Bokang 的“等对方”增加 1；
- 溪岸的“需要我处理”增加 1；
- Bokang 详情显示“下一步：等待溪岸接受交接”和“撤回交接”；
- 溪岸详情显示“下一步：接受或拒绝交接”；
- 任务在此刻主体仍按 Bokang 负责人归组。

撤回只结束该请求，负责人和任务状态不变，撤回事实保留在活动记录。以后再次交接必须新建请求。

### 8.4 屏四：溪岸接受交接

溪岸打开交接请求时看到任务摘要、当前负责人和不可丢失的交接说明，并可以接受或拒绝。

接受后：

- 交接请求结束；
- 负责人从 Bokang 变为溪岸；
- 任务状态保持进行中；
- 双方由该请求贡献的“需要我处理”和“等对方”数字各减 1；
- 溪岸首页任务移动到“我在推进”；
- Bokang 首页任务移动到“溪岸在推进”；
- 溪岸详情显示“下一步：继续处理任务”。

拒绝后，任务仍由 Bokang 负责且保持进行中，拒绝事实保留。再次发起交接必须创建新请求。

### 8.5 屏五：溪岸提交验收

接受交接并推进后，溪岸填写本次验收内容并提交。提交动作同时建立以下产品事实：

- 负责人仍是溪岸；
- 任务从进行中进入待验收；
- 新的验收请求发给 Bokang；
- 溪岸的“等对方”增加 1；
- Bokang 的“需要我处理”增加 1；
- 任务从此刻首页三个主体分组移出；
- 溪岸详情只显示“下一步：等待 Bokang 验收”，没有“通过、退回”按钮；
- Bokang 通过“需要我处理”进入验收页。

验收内容随本次请求保存，不因任务描述后续变化而被覆盖。原型使用文字内容验证这项语义，不扩展附件系统。

### 8.6 屏六：Bokang 通过或退回

Bokang 看到溪岸提交的验收内容，并看到“下一步：确认验收结果”和两个动作。

通过后：

- 验收请求结束；
- 任务进入已完成；
- 负责人字段仍记录溪岸，不改成验收人；
- 双方对应的请求入口数字各减 1；
- 任务不回到此刻主体，可在“全部事情”中找到；
- 完成详情展示提交的验收内容、验收人 Bokang 和验收时间。

退回时必须填写具体原因。退回后：

- 验收请求以退回结果结束；
- 任务回到进行中；
- 负责人仍是溪岸；
- 双方对应的请求入口数字各减 1；
- 溪岸首页任务回到“我在推进”，Bokang 首页任务回到“溪岸在推进”；
- 溪岸详情显示“下一步：修改后重新提交验收”和退回原因；
- Bokang 详情显示相同退回事实，但没有替溪岸重新提交的主按钮。

溪岸修改后再次提交时必须产生新的验收请求；上一条退回请求及其原因继续保留。

## 9. 双方视角与数字变化验收表

下表中的 `+1` 和 `0` 表示这条示例任务对入口数字的贡献，不代表页面上其他示例数据的绝对总数。

| 阶段 | 任务事实 | Bokang 此刻 | 溪岸此刻 | Bokang 请求贡献 | 溪岸请求贡献 |
| --- | --- | --- | --- | --- | --- |
| Bokang 推进 | Bokang · 进行中 | 我在推进 | Bokang 在推进 | 处理 0 / 等待 0 | 处理 0 / 等待 0 |
| 等待接受交接 | Bokang · 进行中 | 我在推进 | Bokang 在推进 | 处理 0 / 等待 +1 | 处理 +1 / 等待 0 |
| 溪岸接受 | 溪岸 · 进行中 | 溪岸在推进 | 我在推进 | 处理 0 / 等待 0 | 处理 0 / 等待 0 |
| 等待 Bokang 验收 | 溪岸 · 待验收 | 主体不显示 | 主体不显示 | 处理 +1 / 等待 0 | 处理 0 / 等待 +1 |
| Bokang 通过 | 溪岸 · 已完成 | 主体不显示 | 主体不显示 | 处理 0 / 等待 0 | 处理 0 / 等待 0 |
| Bokang 退回 | 溪岸 · 进行中 | 溪岸在推进 | 我在推进 | 处理 0 / 等待 0 | 处理 0 / 等待 0 |

若该任务在当前自然周到期，它在待进行、进行中、阻塞中和待验收阶段都对“本周到期”贡献 1；进入已完成或已取消后贡献 0。它是否同时出现在“本周到期”入口页面，不影响此刻主体的单次归组。

## 10. 活动记录是协作证据

当前状态回答“现在是什么情况”，活动记录回答“为什么会变成这样”。活动记录不能退化为没有内容的“某人修改了任务”。原型至少表达：

```text
Bokang 发起交接
  交接给：溪岸
  交接说明：酒店后续需要持续沟通，请继续跟进合同

溪岸接受交接
  负责人由 Bokang 变为溪岸

溪岸提交验收
  验收内容：已确认酒店合同与套餐

Bokang 退回验收
  原因：请补充取消条款的确认结果
```

每条关键事实还应显示操作者和时间。生产实现需要保证活动、请求结果和任务变化的一致事务与同步，但本地原型只验证信息层级和可理解性。

## 11. 原型验收标准

1. 打开原型首先进入「清单 → 此刻」，不是营销页、近期列表或全部任务。
2. 首页固定显示“需要我处理、等对方、本周到期”三个低权重问题入口。
3. 首页主体固定按“卡住的事情、我在推进、对方在推进”排列，任务在主体中只出现一次。
4. 对方逾期只在“对方在推进”组内提前；画面和说明不得暗示跨负责人全局逾期排序。
5. 等待对方但没有待处理请求的阻塞任务不增加“等对方”数字。
6. 所有状态文案统一为待进行、进行中、阻塞中、待验收、已完成、已取消。
7. 普通任务行最多两层主要信息，阻塞任务增加一行真实原因。
8. 可以在同一条任务上切换 Bokang 与溪岸视角，并看见符合当前身份的下一步和按钮。
9. 交接待接受期间负责人保持 Bokang；溪岸接受后负责人一次性变为溪岸。
10. 溪岸提交验收后任务进入待验收；只有 Bokang 能看到通过和退回。
11. 通过进入已完成；退回必须有原因并回到溪岸负责的进行中。
12. 撤回、拒绝和退回不会删除旧请求；重提以新请求表达。
13. “全部事情”能够展示所有截止范围、六种状态和双方的未删除任务。
14. 活动记录保留交接说明、验收内容和退回原因，能够解释当前状态的来源。
15. 原型不得宣称已完成后端持久化、真实权限、双端同步或生产部署。

## 12. 后续施工门禁

浏览器原型评审通过后，才能分别补充生产设计与实施计划。生产施工至少需要再次确定：

- 验收请求与现有统一审批模型的具体类型和 API 契约；
- 交接、验收、撤回、拒绝、退回与任务状态变化的事务和幂等边界；
- 此刻投影、请求计数和本周口径的服务端或客户端派生方式；
- Android 与 Web 的一致导航、权限和同步表现；
- 子任务在首页、入口数字和全部事情中的展示及计数；
- 首页条目上限、折叠、空状态和大数据量表现；
- 网络失败、并发负责人变化、请求冲突和失效后的用户反馈；
- 自动化测试、双用户验收和可访问性检查。

在这些内容形成独立施工规格前，本文件不能被解读为生产功能已经实现。
