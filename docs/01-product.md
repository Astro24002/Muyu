# Muyu 产品需求（v1 目标与现有契约）

> 2026-09-17 同步：最新产品与架构设计基线为 [Muyu 设计交付 v1.0](../Muyu-Codex-Design-and-Implementation.md)，本文是其工程化摘要。目标不代表已经上线；当前实现证据见 [开发状态](./05-development-status.md)，兼容差异见 [v1 契约与交付设计](./superpowers/specs/2026-09-16-muyu-v1-contract-and-delivery-design.md)。真实认证、Workspace、事务与同步继续复用现有云端工程。

## 1. 产品定义

Muyu 是 Android 优先、面向两个人的日常协作产品，包含事项、共享记账、个人打卡和纪念日。

它不追求成为通用 Todo、团队协作平台或复杂的数据分析系统，而是解决两个人日常生活中的几个具体问题：

- 现在正在处理什么；
- 下一步由谁继续；
- 什么事情被阻塞了，为什么；
- 截止时间是否发生过延期；
- 重要日期什么时候到来；
- 任务和子任务经历过哪些变化。

产品核心价值：

> 帮助两个人把拖延变成可见的协作事实，把模糊责任变成明确的下一步，并通过双方确认完成任务闭环。

## 2. 产品边界

这是一个小而精的私人应用程序。

系统只服务于一个最多两名成员共同使用的私人 Workspace，不提供以下平台化能力：

- 第三位成员；
- 多 Workspace 切换、Team、Organization；
- 多租户；
- RBAC 和复杂权限；
- 公开分享；
- 社交关系；
- 排行榜、积分和惩罚；
- AI 自动规划；
- 面向用户的即时聊天或复杂实时通信。

所有设计优先考虑：少配置、少页面、少打扰、低维护成本。

## 3. 用户模型

用户由手机号唯一标识。首版用户在 Android 上通过短信验证码注册或登录，不使用共享密码或启动时预置账号。

用户 A 在自己的 Android 设备创建 Workspace，并按手机号邀请用户 B；B 完成短信验证并接受邀请后加入。一个 Workspace 最多有两名 ACTIVE 成员，权限完全对等；一个用户在首版最多属于一个 ACTIVE Workspace。

当 Workspace 只有一名 ACTIVE 成员时，系统自动提供一个个人起步分类，使用户无需等待另一位成员或分类审批即可创建任务。起步阶段任务负责人只能是当前用户，但任务不能直接完成；任务必须等第二名成员加入后由负责人提交验收。第二名成员正式加入后，起步分类转为只读迁移分类，新增任务使用双方批准的共享分类。

每次短信验证成功都会让当前 Android 登录设备成为 `ACTIVE` 且可读写，不创建设备审批请求，也不要求另一位成员确认。用户只能在自己的账号内撤销其他设备，当前设备不能撤销；Web 只能由当前用户自己的活动 Android 设备扫码登录，浏览器会话最长 18 小时。当前交付 Android 与 Web；iOS 只保留未来接入空间。

昵称和展示资料不参与权限判断，所有授权都以 `user_id`、Workspace 成员关系和 Device 或 WebSession 状态为准。

### 3.1 Android“我的”概览

“我的”页从现有 Workspace snapshot 派生紧凑的账户概览，不新增统计接口、统计表或统计缓存。当前用户的概览只统计所有未删除且 `current_handler_id` 等于当前用户的 Task；父任务和子任务分别计数，包含全部任务数、未完成数、已完成数、延期次数和累计延期分钟数，累计时长显示为天、小时和分钟。

匹配成功时，账户卡片显示对方头像入口。点击后展示另一位 ACTIVE 成员的同一组概览，统计口径保持一致；快照刷新后更新，刷新失败时保留上一次结果。

任务审批只从 Android “我的”页 AppBar 的审批中心进入；清单、四象限和日程的“更多”菜单不提供任务审批。相邻的 AppBar 操作提供扫码登录 Web。

### 3.2 Android 账户、设备与资料边界

- 短信验证码校验成功后，首次设备和后续设备都直接创建或恢复为 `ACTIVE`，立即拥有当前账号权限；历史未撤销的 `PENDING` 设备在策略迁移中转为 `ACTIVE`，未完成的设备授权请求过期，已撤销设备和审计历史保留。
- 设备管理只允许撤销当前账号下的其他设备。撤销前必须经过客户端二次确认，确认后关联移动会话和刷新令牌失效；当前设备没有撤销入口。
- 个人资料只允许编辑 `display_name`。服务端清理首尾空格，允许清空并统一限制长度；手机号、头像和账号归属不可编辑。页面继续使用现有默认 `CircleAvatar`，不增加头像上传或头像资源接口。
- Workspace bootstrap 的 `match_status` 只由 ACTIVE 成员数量决定：零或一名成员为 `waiting_partner`，两名成员为 `matched`。未匹配时始终显示默认占位头像和“匹配中”，不显示虚假的对方身份；匹配后才显示另一位 ACTIVE 成员的名称、脱敏手机号和概览入口。

## 4. 设计原则

### 4.1 记录事实，不替用户决策

用户明确设置重要与紧急两个属性，用于四象限；不根据截止日期偷偷改变紧急性。现有 `quadrant` 可映射为这两个布尔值，不建立重复事实源。禁止系统评分、双方排名、焦虑式排序和自动推荐顺序；用户排序仅是展示偏好。

### 4.2 首页完整且不重复

“此刻”以卡住的事情、我在推进、TA 在推进三段覆盖全部未完成任务，阻塞优先、其余按当前负责人分组。不能只取前五项，也不能因下一棒变化而变更负责人分组。空段保留标题；加载失败与空数据分开显示。

### 4.3 每个任务都要能说明下一步

任务应当足够具体，能够直接开始。

过大的目标可以拆成一层子任务，例如：

```text
准备婚礼
├── 确定酒店
├── 联系婚庆
└── 整理宾客名单
```

系统不自动拆分任务，只提供清晰的拆分记录。

### 4.4 不隐藏拖延，但不惩罚拖延

延期、阻塞和重复延期都是事实记录，不是失败标记。

系统可以提醒：

> 这个任务已经延期 3 次。

但不进行扣分、排名、羞辱或双方比较。记录的目的只是帮助双方发现任务过大、目标不清晰或等待关系不明确。

## 5. 核心对象

### 5.1 Task

Task 表示需要采取实际行动的事情。

支持：

- 标题和描述；
- 一个当前负责人 `current_handler_id`；
- 计划开始时间；
- 截止时间；
- 预计耗时；
- 开始、完成、取消和重新打开；
- 转交负责人；
- 进入阻塞和解除阻塞；
- 延期；
- 评论；
- 一层子任务。

每项双人阶段的新任务必须且只能属于一个已批准的 Workspace 共享分类。单人阶段由系统自动关联唯一的个人起步分类，用户无需选择分类；该分类不一定出现在普通选择器中。第二名成员加入后，起步分类只允许读取和迁移，不能新建任务或迁入任务。共享分类由一方在“我的 → 分类管理”发起，并经另一方批准后才可选择。分类名称最多五个字符。协议字段暂保留 `labels` 数组名称，但新数据始终只保存一个值（例如 `labels: ["工作"]`）。

### 5.2 Subtask

子任务仍然使用 Task 模型，通过 `parent_task_id` 关联父任务。

第一版只支持一层子任务。父任务和子任务状态相互独立，完成子任务不会自动完成父任务。

父任务即使仍有未完成子任务也可以完成，但界面必须提示确认，并记录该行为。

### 5.3 独立生活领域（目标，尚未实现）

- 共享记账：独立账目，整数分/CNY，收入与支出、付款/收款人与记录人分开；双方可增改、确认删除。月份内全部有效明细决定收支、结余、双方付款和分类汇总，明细筛选不改变汇总。
- 日常打卡：每个习惯归本人，支持每日/自然周/自然月；默认“我的”，可查看“TA 的 / 全部”。只有本人可操作，未开始或暂停不可打卡；有效周期记录唯一，撤销仅影响本期，改频率保留历史快照。确认删除习惯时说明相关打卡记录一并删除，服务端审计仍追加保留。
- 纪念日：保留在“打卡”内，双方可查看和编辑。公历逐年计算，未来原始日期不得提前发生；非闰年 2 月 29 日按 2 月 28 日。准备天数为当天、1、3、7、14、30 天，页内提示不等同于系统推送。
- 手动生成本次准备事项，来源键 `anniversary:{id}:{occurrenceDate}` 在 Workspace 内唯一；生成者负责，初始进行中，截止为本次日期。重复或并发生成返回同一任务；删除/修改纪念日不删除或改写既有任务。

旧 Event/RecurringTask 不作为 v1 的数据模型。不得把打卡重命名为“重复”，不做自动周期生成事项、农历、AA 清算、银行接入或系统推送。

## 6. 任务协作模型

### 6.1 当前负责人、读取与审批

- `current_handler_id` 是唯一负责人，必须是同一 Workspace 的 ACTIVE 成员；创建任务时默认使用创建者。
- 同一 Workspace 的两位 ACTIVE 成员都可以读取全部未删除任务，包括父任务和子任务；“我的任务”只匹配 `current_handler_id == 当前用户`。
- 当前负责人可以直接修改；非当前负责人的另一位成员修改受保护字段时，继续创建发给当前负责人的单人审批请求，由对方成员确认。

两个人经常交换负责人，因此转交是正常操作，不是异常流程。

### 6.2 现有内部状态与 v1 展示

```text
TODO
IN_PROGRESS
BLOCKED
REVIEW
DONE
CANCELLED
```

v1 的 `ACTIVE / BLOCKED / HANDOFF_PENDING / REVIEW_PENDING / DONE` 是产品语义；当前数据库仍保留以下六状态含义，待接棒由审批请求派生，不能新增第二个 owner 或直接替换状态枚举。详细映射及迁移缺口见 v1 契约设计。

状态含义：

- `TODO`：待进行，已创建但尚未开始；
- `IN_PROGRESS`：进行中，当前负责人正在处理；
- `BLOCKED`：阻塞中，当前负责人暂时无法继续；
- `REVIEW`：待验收，当前负责人已提交结果，等待另一位成员确认；
- `DONE`：已完成，验收人已确认结果；
- `CANCELLED`：已取消，任务不再需要执行。

Android 和 Web 的用户界面只展示中文名称，英文值仅作为系统内部标识。

现有 API 允许从 `DONE` 或 `CANCELLED` 恢复并保留历史，这是兼容能力。v1 主流程不新增取消、重开、删除或撤回入口；收敛旧路径必须先制定兼容计划。

### 6.3 阻塞

进入 `BLOCKED` 时必须填写：

- 阻塞原因；
- 解除阻塞后继续处理的用户。

可以额外说明正在等待哪一位用户。

v1 解除阻塞后恢复 `IN_PROGRESS`，负责人不变，历史原因与阻塞时长保留。现有恢复负责人字段的跨人路径须先完成兼容审计，不能将解除阻塞作为绕过交接确认的方式。

任务负责人不能直接将任务改为 `DONE`。双人阶段执行一次“提交验收”后，任务进入 `REVIEW`，并在同一事务中自动创建发给另一位 ACTIVE 成员的任务验收审批；不再要求负责人手动发起第二条审批。验收通过进入 `DONE`，退回必须填写原因并回到 `IN_PROGRESS`。任务负责人不能自行确认自己的 Review。单人阶段没有验收人，提交验收入口保持不可用，任务继续保持 `IN_PROGRESS`，直到另一位成员正式加入。

## 7. 延期记录

延期原因必须填写。每次延期都生成一条不可修改的记录，不能直接覆盖历史。

延期记录包含：

- 原截止时间；
- 新截止时间；
- 延期用户；
- 延期原因；
- 延期时长；
- 补充说明；
- 创建时间。

第一版原因枚举：

```text
NO_TIME
TOO_LARGE
NOT_WILLING
FORGOT
WAITING_PARTNER
INTERRUPTED
OTHER
```

选择 `OTHER` 时必须填写补充说明。

## 8. 并发编辑与冲突

任务编辑采用字段级乐观并发。两端同时修改不同字段时，服务端自动合并；两端修改同一字段，或并发执行状态、完成、恢复、删除等生命周期操作时，服务端保留先成功的权威状态并返回可审计的 `409` 冲突。

冲突记录保存基线值、当前值、提议值、版本和操作者。冲突不会成为任务状态，也不会锁住其他任务或未冲突字段。任一 Workspace 成员都可以保留当前值，或以最新版本重新提交提议值；解决动作会写入操作和活动历史，不要求双方共同签名。

如果任务已经软删除，普通编辑、评论和延期必须先恢复任务。

## 9. 活动记录

任务和子任务的所有变更都需要记录：

- 创建；
- 修改；
- 创建时确定当前负责人；
- 转交负责人；
- 开始；
- 进入阻塞；
- 解除阻塞；
- 延期；
- 完成；
- 取消和恢复；
- 创建子任务；
- 评论；
- 并发冲突产生和解决。

活动记录只允许新增，不允许修改或删除。它用于任务时间线、延期回顾和冲突审计。

## 10. 信息架构与事项阅读

底部固定 `事项 / 记账 / 打卡 / 我的`。事项默认清单“此刻”，标题 `此刻⌄ / 四象限⌄ / 日程⌄` 整体可点，菜单选项为“清单 / 四象限 / 日程”。不恢复独立常驻切换栏、品牌栏、顶部头像或宣传横幅。

- 标题菜单锚定标题，当前项有勾选；点当前项仅关闭，外部点击/返回/Escape 关闭，方向键/Enter 可操作并恢复焦点。约 160ms 淡入，尊重减少动态效果。
- 三视图共享任务源；清单滚动、象限负责人筛选/滚动、日程月份/日期/滚动独立保留。会话内回到事项保留视图，全新会话默认此刻；删除锚点时回到最近有效位置。
- 此刻依次展示标题/日期、简短提示、三个指标、全部事情入口和互斥三段；不在指标下再复制任务卡。
- “需要我处理 / 等对方”仅统计等待接棒或验收的请求，按下一棒区分。“本周到期”按统一业务时区周一至周日，包含本周已逾期未完成任务；三指标不可相加为总任务数。现有审批指标更宽的口径尚需收敛。
- 四象限默认未完成任务，筛选“我们 / 我负责 / TA 负责”；日程是截止日期月视图，周一开始，支持月份、选日、今天，不创建独立日历事件。
- “全部事情”从此刻与我的进入，搜索名称、分类、负责人、下一步；筛选未完成、全部、已阻塞、待验收、待接棒、已完成。兼容已取消历史；详情返回恢复来源上下文。
- 详情先显示任务信息、负责人/状态/截止/象限、下一棒与说明、可执行动作，再显示补充说明和协作记录；不把动作埋进日志。完成记录保留验收人和时间。

## 11. v1 创建与协作

新建必填标题与明确下一步；目标长度为标题 70、下一步 90、操作说明 500、补充说明 1000 Unicode code point，不静默截断旧数据。可配置截止日期、分类、重要、紧急和补充说明；分类继续沿用现有单分类审批契约，不新增项目管理模块。

新建给自己由自己推进；新建给 TA 仍由创建者负责，同时原子创建交接请求，TA 接受后才同时应用负责人和拟下一步。拒绝需要原因，原下一步不变。提交验收需交付说明，只有对方可通过或填写原因退回；单人阶段不能完成。阻塞需原因，解除前不能交接或验收。

用户填写的 `next_step_text` 与当前详情的 viewer-aware `next_step` 投影分开；字段、旧客户端、日期与长度限制迁移依照契约设计实施，不能只修改表单。

完整验收路径：创建 → 交接 → 对方接棒 → 提交验收 → 退回并说明原因 → 再提交 → 通过 → 双方在全部事情查看历史。每步核对负责人、下一棒、指标、分组、活动与 cursor。

### 明确不做

- 多租户和组织体系；
- 复杂权限；
- 社交和公开分享；
- P2P、局域网同步和离线写入队列；
- 首版设备验证审批或把设备审批伪装成任务审批；
- Web 端短信验证码直接登录或浏览器长期设备身份；
- 面向用户的即时聊天和复杂实时通信；
- AI 自动规划；
- 自动任务排序；
- 排行榜、积分和惩罚机制。

## 12. 产品验收原则

每项功能都应回答：

1. 是否让用户更容易开始？
2. 是否让两个人更容易协作？
3. 是否保持首页分组完整互斥、信息易于扫描？
4. 是否保留真实行为记录？
5. 是否避免引入不必要的复杂度？

如果一个功能不能改善上述至少一项，就不进入这个私人应用的核心版本。
