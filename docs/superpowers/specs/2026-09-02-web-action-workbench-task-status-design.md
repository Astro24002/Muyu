# Web 行动工作台任务状态与首页模块设计

## 1. 目的与范围

本规格定义 Muyu Web 端双人协作行动管理系统的任务状态展示、状态转换和“今天”行动工作台内容边界。

Muyu 只服务于一个最多两名成员的私人 Workspace。Web 端不是企业后台，也不是通用项目管理平台；它的主要职责是帮助当前用户明确自己的下一步，并在任务无法继续或需要对方确认时，给出清晰的协作动作。

本规格覆盖：

- 用户可见的六种任务状态；
- `Blocked` 阻塞原因和等待信息；
- `Review` 待验收流程；
- “今天”页的当前任务、当前阻塞和待我验收模块；
- 当前用户任务的筛选、排序和数量限制；
- 状态在列表、详情和首页中的统一表达。

本规格不增加管理员、项目层级、团队层级、自定义工作流或多人审批，也不改变双人 Workspace 的读取和负责人权限模型。

## 2. 产品心智模型

首页只回答当前用户的三个问题：

1. 我现在可以推进什么？
2. 我负责的事情为什么暂时不能推进？
3. 现在有哪些事情需要我确认？

因此，首页不展示对方的一般任务、对方的进度或对方的工作量。只有当某个协作事件直接要求当前用户行动时，它才可以出现在首页，例如待验收或待审批。

任务负责人仍然只有一个 `current_handler_id`。两位成员都可以读取 Workspace 内全部未删除任务，但“今天”页默认以当前登录用户为中心筛选内容。

## 3. 用户可见状态

Web 端向用户展示以下六种状态：

```text
待进行 Todo
进行中 In Progress
阻塞中 Blocked
待验收 Review
已完成 Done
已取消 Cancelled
```

英文标识用于接口、状态选择器和测试，正式界面优先显示中文名称。状态颜色不能单独承担语义，列表中必须同时显示文字或可访问名称。

### 3.1 状态含义

| 状态 | 含义 | 是否进入“当前任务” |
| --- | --- | --- |
| `TODO` | 已记录但尚未开始 | 是 |
| `IN_PROGRESS` | 当前负责人正在执行 | 是 |
| `BLOCKED` | 当前负责人无法继续，需要外部条件或他人响应 | 否 |
| `REVIEW` | 当前负责人已提交结果，等待另一位成员验收 | 否 |
| `DONE` | 结果已被验收，任务结束 | 否 |
| `CANCELLED` | 任务不再需要执行 | 否 |

`Blocked` 和 `Review` 都是有效工作状态，不表示失败。它们从“当前任务”移出，是因为当前用户此刻不能直接按普通执行动作推进它们。

### 3.2 状态转换

推荐的主要转换如下：

```text
TODO ───────────────→ IN_PROGRESS ─────────────→ REVIEW ─────→ DONE
  │                         │                      │
  │                         └──────→ BLOCKED       └──────→ IN_PROGRESS
  │                                    │
  └────────────────────────────────────┘

TODO / IN_PROGRESS / BLOCKED / REVIEW / DONE
    └────────────────────────────────────────→ CANCELLED

DONE / CANCELLED ─────→ TODO 或 IN_PROGRESS
```

具体允许的转换仍由服务端状态机约束。恢复、取消和重新打开必须保留活动历史，不能通过直接覆盖字段隐藏过程。

## 4. Blocked 阻塞设计

### 4.1 进入阻塞的规则

只有当前负责人可以直接将任务设置为 `BLOCKED`。另一位成员尝试改变该任务状态时，沿用现有双人审批规则，由当前负责人确认。

进入 `BLOCKED` 时必须填写阻塞原因。原因不能是空白，也不能只依赖一个枚举值；用户需要能说明任务为什么无法继续。

阻塞表单至少包含：

```text
阻塞原因       必填文本
等待对象       可选：对方 / 外部条件
恢复负责人     必填：解除阻塞后由谁继续处理
```

系统事实字段保持为：

```text
blocked_reason
blocked_since
waiting_for_user_id
resume_handler_id
```

`blocked_since` 由服务端写入，不能由 Web 客户端伪造。`resume_handler_id` 用于解除阻塞后确定下一位负责人；它不等同于“等待对象”。例如可以等待外部机构，但解除后仍由当前用户继续处理。

### 4.2 “今天”页的当前阻塞模块

首页第二个模块固定命名为：

```text
当前阻塞
```

它只显示当前用户负责的 `BLOCKED` 任务，不显示对方负责的阻塞任务。每条阻塞项展示：

- 任务标题；
- 阻塞原因；
- 等待对象，若未填写则显示“外部条件”；
- 已阻塞时长；
- 截止时间及临期提醒；
- 打开任务详情的动作。

示例：

```text
当前阻塞  2

确认出行日期
等待对方确认最终日期
等待对方 · 已阻塞 2 天 · 明天到期       查看任务

准备入住材料
等待外部机构发送证明文件
等待外部条件 · 已阻塞 5 小时             查看任务
```

阻塞任务不提供普通的“完成”主按钮，因为它当前没有可确认的完成结果。详情页可以提供“解除阻塞”动作；解除成功后任务转为 `IN_PROGRESS`，清除当前阻塞展示字段，并按当前任务规则重新排序。

### 4.3 阻塞模块的排序与数量

当前阻塞按以下顺序排列：

1. 已逾期任务；
2. 即将到期任务；
3. 阻塞时间最长的任务；
4. 最近更新的任务。

首页默认最多显示 3 项。超过 3 项时显示“查看全部”，进入所有任务并保留 `Blocked` 筛选。阻塞模块使用浅珊瑚色提示和明确文字，不使用错误红色，也不显示惩罚、评分或双方比较。

## 5. Review 待验收设计

### 5.1 进入待验收

当前负责人完成自己的执行工作后，可以将任务从 `IN_PROGRESS` 设置为 `REVIEW`。提交时可以补充结果说明或下一步信息；服务端保留状态变化和活动记录。

任务进入 `REVIEW` 后，当前负责人保持为提交人，另一位 ACTIVE 成员自动成为默认验收人。系统不引入额外的验收角色、多人投票或管理员批准。

### 5.2 验收动作

验收人可以执行两个动作：

```text
通过验收       REVIEW → DONE
退回修改       REVIEW → IN_PROGRESS
```

退回修改必须填写原因，例如：

```text
还需要补充订单截图
```

验收通过时记录验收人和时间；退回时记录退回原因和活动记录。验收过程中任务不能被普通完成按钮直接跳过，也不能由提交人自行确认完成。

### 5.3 “今天”页的待我验收模块

待验收不是当前用户负责的普通任务，因此不进入“当前任务”和“当前阻塞”。当当前用户是 `REVIEW` 任务的默认验收人时，首页显示独立模块：

```text
待我验收
```

每条内容展示：

- 任务标题；
- 提交人；
- 结果说明或描述摘要；
- 截止时间；
- “查看并验收”入口。

这个模块只展示明确要求当前用户做决定的任务，不展示对方的其他任务或工作进度。验收通过、退回后，该任务立即从本模块消失；若退回，任务重新由原负责人处理，不会进入当前用户的任务列表。

首页默认最多显示 3 项。超过数量时显示“查看全部”，进入所有任务的 `Review` 视图或审批中心对应入口。

## 6. 当前任务模块

首页第一个核心模块固定命名为：

```text
当前任务
```

它只显示当前负责人是当前用户的任务，最多 5 项。候选状态只有：

```text
TODO
IN_PROGRESS
```

候选任务不包含 `BLOCKED`、`REVIEW`、`DONE`、`CANCELLED`，也不包含已删除任务。

### 6.1 排序规则

排序按行动紧迫性计算，不保存新的业务优先级字段：

1. 已逾期任务优先；
2. 有截止时间的任务按截止时间从近到远；
3. 没有截止时间的任务排在有截止时间任务之后；
4. 截止时间相同时，最近更新的任务优先；
5. 仍相同时，使用任务 ID 做稳定排序。

`IN_PROGRESS` 和 `TODO` 混排，进行中任务不因为状态名称而自动压过更早到期的待办任务。系统只取排序后的前 5 项。

### 6.2 展示方式

当前任务使用一个线性任务区域，不使用五张并列大卡片。每项固定高度，展示：

```text
状态标记  任务标题  负责人  截止时间  标签或进度  操作
```

当前用户不需要在任务行中看到自己的完整用户信息，负责人可显示为“我”。已逾期和临期通过文字加颜色表达；颜色不替代“已逾期”“今天 18:00”等明确文案。

任务完成后，下一条符合规则的任务自动补入，保持最多 5 项的行动队列。

## 7. 首页整体结构

“今天”页建议固定为以下顺序：

```text
今天，先让一件事向前走

快速记录

当前任务                         最多 5 项
只显示 Todo / In Progress

当前阻塞                         最多 3 项
只显示我负责的 Blocked 任务和阻塞原因

待我验收                         最多 3 项
只显示明确要求我确认的 Review 任务

同步状态与错误                   低权重显示
```

空模块直接省略，不显示空白卡片：

- 没有当前任务时显示“今天没有需要处理的任务”和“记下一件事”；
- 没有当前阻塞时不显示“当前阻塞”；
- 没有待验收时不显示“待我验收”。

对方的一般任务、对方负责的阻塞任务、对方进行中的任务和普通活动记录全部不在今天页展开。它们只能通过“所有任务”和“动态”入口查看。

## 8. 详情页与列表的一致性

任务详情页必须展示与首页相同的状态名称和状态语义。状态选择器根据当前状态和权限只提供合法动作：

- `TODO`：开始、取消；
- `IN_PROGRESS`：提交验收、阻塞、完成或取消；
- `BLOCKED`：解除阻塞、取消；
- `REVIEW`：通过验收、退回修改；
- `DONE`：重新打开或取消；
- `CANCELLED`：重新打开。

具体按钮仍受负责人、审批和服务端冲突结果约束。不能因为 Web 本地显示了按钮，就绕过服务端权限或审批流程。

列表、看板和详情都读取同一个任务快照；看板只是状态的投影，不保存另一套状态。任何状态变化完成同步后，首页三个模块应立即按照上述规则重新计算。

## 9. 与当前实现的迁移关系

当前代码中仍使用 `WAITING` 表示阻塞状态，且尚未包含 `REVIEW`。后续实施需要把用户可见状态和服务端状态机统一迁移为：

```text
WAITING → BLOCKED
新增 REVIEW
```

迁移必须同时覆盖：

- 后端枚举、状态转换和请求校验；
- `blocked_reason`、`blocked_since`、`resume_handler_id`、`waiting_for_user_id` 的读写；
- Review 的提交、通过和退回接口或统一状态转换接口；
- Web 和 Android 的状态模型、文案、筛选和测试；
- 快照、增量变更、活动历史和审批投影。

如果服务端暂时不能一次完成迁移，Web 可以在短期适配层中把旧 `WAITING` 映射为用户可见的 `BLOCKED`，但不能把 `WAITING` 和 `BLOCKED` 同时暴露给用户，也不能用 Review 文案伪装普通完成。

## 10. 验收标准

1. Web 用户只能看到六种任务状态：Todo、In Progress、Blocked、Review、Done、Cancelled。
2. `Blocked` 进入时必须填写阻塞原因，并能展示等待对象和阻塞时长。
3. 当前任务最多 5 项，只包含当前用户负责的 Todo 和 In Progress。
4. 当前任务按逾期、截止时间、更新时间和稳定 ID 排序，完成一项后自动补足。
5. 当前阻塞只包含当前用户负责的 Blocked 任务，最多 3 项，并展示阻塞原因。
6. Review 默认由另一位成员验收，通过进入 Done，退回进入 In Progress 且必须有退回原因。
7. 待我验收只显示明确要求当前用户操作的 Review 任务，不展示对方一般任务。
8. 今天页不展开对方任务、对方进度或普通对方动态。
9. 状态、颜色、图标和文案在首页、列表、看板和详情中保持一致。
10. 阻塞、待验收、审批、同步失败和冲突都有文字化、可访问的状态表达。
11. 状态变化、阻塞原因、验收结果和退回原因均保留活动历史。
12. 后续实现必须补充 Web、Android、后端状态转换和同步协议的回归测试。
