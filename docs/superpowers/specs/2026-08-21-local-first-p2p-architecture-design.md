# Local-first P2P 双人同步架构设计

## 1. 设计状态与决策范围

本规格定义项目从“服务端保存任务状态”转向“两个 Android 客户端直接同步本地事件”的架构边界。它是架构级变更，先于实现计划和代码改造生效。

本规格取代以下运行时假设：

- FastAPI/PostgreSQL 是任务事实源；
- JWT、Refresh Session 和手机号登录是任务同步的身份基础；
- 服务端通过 status_version 和 HTTP 409 解决状态冲突；
- ECS 或其他云端中继保存任务数据。

现有服务端代码和 Phase 0-3 数据库作为历史实现保留，直到新的 P2P 垂直切片完成；它们不参与新架构的任务数据路径。现有的 [Phase 4 状态冲突规格](./2026-08-19-status-conflicts-design.md) 尚未实现，后续不按其中的服务端冲突方案实施。

## 2. 目标

目标是建立一个只依赖两台 Android 设备的 local-first 双人协作系统：

- 每台设备都可以在离线时创建和追加事件；
- P2P 是唯一的同步路径，连接恢复后双向补齐缺失事件；
- 本地追加式 Event Store 是事实源，当前任务状态只是可重建的物化投影；
- 设备身份、事件签名和事件加密在本地完成；
- 状态并发不使用最后写入覆盖，而是进入确定性的业务冲突解决流程；
- 换机由另一方现有可信设备批准；
- 连接中断、重复传输、应用崩溃和物化表损坏不会静默丢失或覆盖事实。

## 3. 范围与非目标

### 3.1 本阶段包含

- Android 作为唯一完整节点；
- 两个固定成员槽位，每位成员同时只有一台活动设备；
- 本地设备身份、工作区初始化、二维码/短码接触匹配；
- Android Keystore 保护的设备私钥；
- SQLite 追加式 Event Store 和可重建物化表；
- 局域网或一台设备热点上的直连传输；
- 可替换的 PeerTransport 接口；
- 事件签名、每设备 hash 链、因果上下文和事件级 AEAD 加密；
- 追加式事件合并、状态冲突记录、双方确认和冲突审计；
- 换机、旧设备撤销和 Epoch 密钥轮换；
- 断线续传、幂等接收、隔离异常事件和本地重建。

### 3.2 明确不包含

- ECS、公有云中继、云端备份和云端恢复；
- 服务端参与任务事实、解密、合并或冲突审批；
- Flutter Web 作为完整同步节点；
- 同一成员的多台并行活动设备；
- 第三个成员、多人群组密钥或多租户；
- Push、WebSocket、消息队列和公网同步；
- 使用手机号、密码、JWT 或服务端 Session 作为 P2P 身份；
- 双设备都丢失时的历史恢复；
- 现有 PostgreSQL 任务数据的自动迁移；
- 彻底擦除已经在设备上解密过的明文。

## 4. 总体架构

    设备 A：Local Unlock -> Android Keystore -> Device Identity Keys
           -> SQLite Event Store -> Materialized State -> Conflict Index
                             <-> 二维码配对 / 局域网或设备热点
    设备 B：Local Unlock -> Android Keystore -> Device Identity Keys
           -> SQLite Event Store -> Materialized State -> Conflict Index

两台设备都保存事件密文和本地物化状态。设备之间传输的是已签名的事件信封；局域网连接只负责传输，不成为事实源。没有第三个中心节点。

现有 FastAPI/PostgreSQL 服务保留为旧阶段工程和测试环境，不被新 P2P 客户端调用。新的客户端架构不能依赖 API 可用性才能创建、查看或修改任务。

## 5. 工作区和设备拓扑

### 5.1 固定成员槽位

一个工作区最多有两个逻辑成员槽位：A 和 B。成员身份与设备身份分离：

    成员 A -> 设备 A1 -> 换机后设备 A2
    成员 B -> 设备 B1 -> 换机后设备 B2

首版约束为：每个成员同时只有一台 ACTIVE 设备。换机替换成员槽位的设备，不创建第三个成员，也不改变成员的历史身份。

### 5.2 首次初始化

1. 设备 A 创建工作区、生成 workspace_genesis 事件并占用成员槽位 A；
2. A 生成一次性配对邀请，二维码/短码只包含工作区标识、邀请随机数、A 的公钥和临时传输信息，不包含明文任务或私钥；
3. 设备 B 扫描邀请，双方显示并人工核对同一短码；
4. A 批准 B，B 返回自己的设备公钥和成员接受签名；
5. 双方写入配对记录和初始 Epoch 密钥包后，B 才成为 ACTIVE。

配对记录必须原子落盘。二维码过期、连接中断或任一签名验证失败时，不得留下半个成员或半个可信设备。

### 5.3 换机和撤销

如果成员 A 更换设备：

1. 新 A 生成全新的设备身份密钥；
2. 新 A 与现有 B 设备通过二维码/短码接触匹配；
3. B 核对短码并明确批准新 A；
4. B 将历史 Epoch 密钥重新封装给新 A，并生成设备替换事件；
5. 旧 A 设备标记为 REVOKED，当前 Epoch 轮换；
6. 新 A 获得历史事件读取能力和新的写入 Epoch 后成为 A 槽位的唯一活动设备。

被撤销设备即使重新上线也不能建立新的同步会话。旧设备已经取得的历史明文或旧 Epoch 密钥无法通过撤销追回；撤销只保证它不能读取后续 Epoch 的新事件。

如果成员 B 更换设备，流程完全对称。两台活动设备都丢失时，本阶段没有云端副本或恢复材料，历史不可恢复，只能在新设备上建立新的工作区。

## 6. 本地身份和解锁

每台设备生成两组相互分离的密钥：

- 签名密钥：证明事件和配对消息来自该设备；
- 密钥交换密钥：接收工作区 Epoch 密钥和建立同步会话。

首版使用 Ed25519 作为事件签名、X25519 作为密钥交换、SHA-256 作为哈希。实现必须使用经过审查的密码库，不得自行实现密码学原语或自定义椭圆曲线算法。

私钥永远不离开设备。Android Keystore 保存不可导出的设备保护密钥，并用于保护应用数据库中的私钥密文；私钥明文只在完成本地解锁后短暂进入内存。具体的本地解锁方式可以使用系统 PIN、密码或生物识别，但解锁凭据不作为同步数据，也不直接派生工作区密钥。

成员槽位通过工作区配对记录和成员签名识别。设备替换不会继承旧设备的私钥，而是由现有可信设备批准新的设备公钥，并将该成员槽位转移到新设备。手机号、昵称、角色和其他资料不是 P2P 身份凭据，需要同步的资料必须通过事件记录。

## 7. 密钥层级和事件加密

    设备身份私钥
      -> 解封分配给该设备的 Epoch Key
      -> Epoch Key 解封单个事件的 DEK
      -> DEK 解密事件内容

- Epoch Key：工作区在一个设备信任周期内使用的随机 256 位密钥；换机或撤销时生成新 Epoch；
- Event DEK：每个事件独立生成的随机 256 位密钥；
- 事件载荷：使用 AES-256-GCM 加密，事件头作为 AAD，随机 nonce 不重复使用。

同一个事件只生成一份密文。事件 DEK 使用当前 Epoch Key 封装，Epoch Key 再分别使用每台活动设备的公钥封装。两台设备得到相同事件密文，但各自用自己的私钥解封自己的 Epoch Key。

密钥封装和会话密钥派生使用经过审查的 X25519/HKDF/AEAD 封装实现；实现不得把登录密码、设备序号或可预测业务字段直接当作密钥。

新 Epoch 只用于未来事件。旧 Epoch 保留在可信设备上，用于读取旧历史；换机时现有设备将仍需保留的历史 Epoch 重新封装给新设备。撤销设备后，后续事件不再给被撤销设备封装新 Epoch。首版不提供本地历史密钥垃圾回收，避免两台设备对删除确认达成一致前产生不可逆分歧。

## 8. Event Store 和事件信封

SQLite 中的 events 表是唯一事实源，事件只允许追加，不允许更新或物理删除。materialized_tasks、冲突索引和列表统计都是由事件重放得到的缓存。

事件写入、签名验证结果和投影更新必须在同一个本地事务边界内提交。事件已经落盘但投影更新失败时，启动恢复流程重新重放；未提交事务全部回滚。

每个事件至少包含以下字段：

    workspace_id
    event_id
    member_id
    origin_device_id
    event_type
    schema_version
    device_sequence
    previous_hash
    causal_context
    epoch_id
    nonce
    encrypted_dek
    ciphertext
    ciphertext_hash
    created_at
    signature

事件头使用规范 CBOR 编码后参与签名。previous_hash 只连接同一设备的上一条事件，形成每设备独立追加链；不存在跨设备的全局单链。

causal_context 是设备序号向量，记录创建事件时已知的每台设备最大序号。它用于判断因果先后或并发，不用于替代签名和 hash 链。created_at 只用于展示和审计，不作为冲突胜负依据。

事件签名覆盖除 signature 外的规范信封，ciphertext_hash 用 SHA-256 校验密文完整性。接收方必须验证来源公钥、签名、设备序号、previous_hash、密文哈希和工作区标识后才能进入有效 Event Store。

任务领域至少使用以下追加式事件：

    WorkspaceGenesis
    MemberJoined
    DeviceAdded
    DeviceReplaced
    DeviceRevoked
    EpochRotated
    TaskCreated
    TaskFieldPatched
    TaskAssigneeAdded
    TaskAssigneeRemoved
    TaskStatusChanged
    TaskDelayRecorded
    TaskCommentAdded
    TaskDeleted
    ConflictApproval
    ConflictResolved
    ConflictSuperseded

延期、评论、活动审计和删除都通过新增事件表达。TaskDeleted 只改变物化视图的可见性，不能删除创建、状态或延期历史。

## 9. 本地物化状态

客户端把本地持久化拆成以下职责：

    identity_store       设备密钥、成员槽位和信任关系索引
    event_store          追加式事件信封和验证状态
    epoch_key_store      当前设备可解封的 Epoch Key 包
    sync_state           对端设备链头、已确认游标和断点
    conflict_store       从事件派生的 OPEN/RESOLVED/SUPERSEDED 索引
    materialized_state   任务、参与人、延期和展示查询

UI 不直接写表。领域命令生成事件，Event Store 持久化事件，投影器再更新物化状态。删除并重建 materialized_state 后必须能从有效事件得到相同结果。

状态冲突未解决时，物化层保留最后一个已确认的共享状态，并单独保存每个候选分支；UI 可以显示本设备的暂定提议，但不得把某一分支静默标记为双方共同状态。

## 10. P2P 接触匹配和传输

### 10.1 传输抽象

同步协议通过以下抽象隔离具体网络技术：

    PeerTransport
      discover()
      connect(invite)
      accept()
      send(frame)
      receive()
      close()

首版实现 LocalNetworkTransport：使用同一局域网或一台设备开启热点，二维码/短码传递一次性邀请和连接信息。未来可以增加 Android Nearby 等实现，但不能修改事件格式、密钥层或合并器。

### 10.2 会话状态机

    DISCOVER
      -> AUTHENTICATE
      -> EXCHANGE_HEADS
      -> PLAN_MISSING_EVENTS
      -> TRANSFER_BIDIRECTIONAL
      -> VERIFY_AND_COMMIT
      -> MERGE
      -> ACK
      -> DONE

AUTHENTICATE 使用双方长期设备身份签名临时会话密钥，建立额外的认证加密通道。通道加密只保护传输过程，不能替代事件自身的签名和事件级加密。

双方先交换协议版本、工作区标识、设备 ID、当前 Epoch、每设备链头、事件头索引和同步游标，再计算双向缺失事件。事件以分块形式传输，每个分块带长度和哈希；接收方完成验证并写入事务后才发送 ACK。

### 10.3 断线和重复

- 连接中断后只重新请求未确认事件；
- 事件按 event_id 幂等，重复事件不重复应用；
- 已验证并落盘的事件不因会话失败回滚；
- 链存在缺口时先进入待验证区，请求缺失前置事件；
- 事件哈希、签名或工作区不匹配时进入隔离区，不更新任务状态；
- 被撤销设备在认证阶段拒绝，不进入事件交换。

## 11. 事件合并和状态冲突

### 11.1 因果分类

收到事件后，合并器按 causal_context 分类：

- 已存在相同 event_id：忽略；
- 当前本地事件因果包含远端事件：按正常顺序重放；
- 远端事件因果包含本地事件：补齐后按因果顺序重放；
- 双方互不包含：视为并发候选，交给事件类型规则。

### 11.2 自动合并规则

- 延期、评论和活动事件：按 event_id 去重后全部保留；
- 普通字段：按字段合并；因果更新优先；真正并发时使用稳定的 origin_device_id、device_sequence、event_id 作为展示值排序，输掉的事件仍留在历史；
- 参与人集合：使用带唯一操作标识的增删操作，离线新增不会覆盖另一端新增；
- 删除：追加 TaskDeleted，不物理删除事件；
- 状态：不使用最后写入覆盖，进入状态候选和冲突流程。

### 11.3 状态候选和共享投影

每个状态操作生成一个带完整载荷和基准因果上下文的 TaskStatusChanged 事件。没有发现并发分支时，它可以成为新的共享状态；发现同一基准下的不同并发状态时，合并器建立确定性的 conflict_id，其输入包括任务 ID、共同基础因果前沿和候选事件 ID 集合。

冲突 OPEN 时：

- 共享投影停留在最后已确认状态；
- 候选状态和完整载荷单独展示；
- UI 可以显示本设备的本地暂定提议；
- 禁止该任务继续发起状态操作；
- 允许标题、描述、延期、评论等非状态事件继续追加；
- 若另一台离线设备在尚未知道冲突时已经写入新的状态事件，合并器将重新计算候选集合并使旧审批失效。

### 11.4 双方确认

双方分别创建 ConflictApproval 事件，必须绑定：

    conflict_id
    candidate_set_hash
    target_state_hash
    完整目标状态和 WAITING 载荷

两名成员对相同候选集合和完整目标状态确认后，任一设备都可以生成 ConflictResolved 事件。该事件引用两条审批事件和双方签名，使用确定性事件 ID 幂等。目标状态必须从冲突的共同基础状态合法转换；如果目标已经等于当前共享状态，不重复写状态变化，但仍记录解决事件。

如果目标不同、候选集合发生变化或期间已有更高因果前沿，旧审批不能使用。冲突保持 OPEN，或者由带有 superseded_conflict_ids 和新候选集合哈希的 ConflictSuperseded 事件明确覆盖为 SUPERSEDED；不能根据上传时间自动判定解决。替代事件本身必须经过事件签名和因果验证，重复替代按 event_id 幂等。

## 12. 删除、丢失和不可恢复边界

删除任务只追加 TaskDeleted，历史事件继续保留。首版没有云端副本，也没有独立恢复份额；两台设备都丢失时，旧工作区历史不可恢复。

设备撤销不能抹除该设备已经读取的明文或旧 Epoch 密钥。应用可以阻止未来同步并轮换新 Epoch，但不承诺对已经解密的内容进行远程擦除。

未来如加入加密导出文件或其他离线恢复介质，必须作为独立规格，不得把它隐含为当前 P2P 方案的一部分。

## 13. 异常和安全语义

    签名/哈希失败    -> 隔离事件，不应用
    链存在缺口       -> 请求前置事件，不确认当前事件
    网络中断         -> 保留已提交事件，断点续传
    重复事件         -> event_id 幂等
    应用崩溃         -> 未提交事务回滚，启动后重放
    投影损坏         -> 删除投影并从事件重建
    未知 Epoch       -> 保留密文，等待可信设备补发密钥包
    设备已撤销       -> 握手拒绝
    冲突未解决       -> 只限制该任务状态操作
    两台设备都丢失   -> 当前版本无法恢复

威胁模型包含局域网窃听、配对过程中的中间人、传输篡改、重复/回滚事件和遗失设备。不包含已经解锁的可信设备被完全攻破、用户主动泄露明文或设备屏幕被拍摄等端点失陷场景。二维码短码必须人工核对，否则不能声称完成防中间人配对。

## 14. 客户端模块边界

新 Flutter 客户端按以下职责拆分：

    identity/       成员槽位、设备密钥、Keystore、配对和撤销
    crypto/         AEAD、签名、密钥封装、规范编码和哈希
    workspace/      工作区初始化、成员和 Epoch 生命周期
    event_store/    SQLite 事件追加、验证状态、事务和重放
    projection/     任务/延期/评论/活动物化查询
    sync/           会话状态机、游标、缺失计划、分块和 ACK
    transport/      LocalNetworkTransport 及 PeerTransport 接口
    conflict/       候选集、审批、解决事件和冲突索引
    presentation/   任务界面、配对界面、同步状态和冲突界面

领域命令只能通过事件写入接口改变数据。sync 依赖 transport、crypto 和 event_store，不依赖具体 UI；presentation 不直接操作网络或密钥。

## 15. 兼容和迁移边界

新的 P2P 首版从新建工作区开始。现有 PostgreSQL 中的任务、延期和活动不自动迁移，因为它们没有原始设备签名、因果上下文和完整事件链。现有后端和数据库作为 Phase 0-3 历史实现保留，不作为新客户端运行时依赖。

如未来需要保留旧任务，只能设计一次性“服务端快照导入”：新设备明确把快照标记为外部导入、由本地设备重新签名，并不能伪装成原始离线事件。该导入不属于本规格。

## 16. 测试和验收

### 16.1 密码学和事件层

- 固定测试向量覆盖规范编码、签名验证、hash 链、AES-GCM 加解密、密钥封装和错误 nonce；
- 篡改任意头字段、密文、签名、序号或前置 hash 都必须被拒绝；
- 事件 ID、设备序号和重复接收必须幂等；
- 投影删除后从同一事件集合重建得到相同状态。

### 16.2 同步层

- A/B 各自离线追加后双向同步，双方事件集合和物化状态一致；
- 同一批事件重复发送、乱序发送和中途断线后续传不丢失；
- 链缺口先补前置事件，异常事件进入隔离区；
- 未信任或已撤销设备无法建立同步会话；
- LocalNetworkTransport 通过 fake transport 运行协议状态机测试。

### 16.3 冲突层

- 同一任务同一基础状态的并发不同状态不会静默覆盖；
- 不同类型的追加事件全部保留；
- 双方同意同一完整目标状态后生成一个幂等 ConflictResolved；
- 双方意见不同、候选集合变化或新的因果前沿出现时，旧审批失效；
- OPEN 冲突只阻止该任务的状态命令，不阻止普通字段、延期和评论；
- 所有分支、审批、解决和替代事件都能在时间线中审计。

### 16.4 设备生命周期

- 首次 A/B 配对只能产生两个成员槽位；
- 换机由另一方可信设备批准，新设备继承成员槽位但使用新设备密钥；
- 换机后旧设备被拒绝同步，未来 Epoch 不能被旧设备解封；
- 本地 Event Store 损坏时可以从另一台设备补齐并重建；
- 两台设备同时丢失时明确显示不可恢复，而不是伪造空数据或从服务端读取。

## 17. 不变量和实现约束

实现完成前必须始终满足：

1. 任何有效任务事实都至少对应一个已签名追加事件；
2. 没有设备私钥，不能伪造该设备事件；
3. 没有成员批准，不能替换成员槽位设备；
4. 没有目标状态的双方签名，不能结束状态冲突；
5. 传输路径不能成为事实源，也不能决定冲突胜负；
6. 物化表可以删除并由有效事件重建；
7. 旧服务端 API 不可被新客户端作为隐式后门或同步依赖；
8. 事件密文、私钥和本地解锁凭据不离开对应设备。
