## 当前补充：Android“我的”、设备与匹配

当前路线的 Android 账户边界如下：

- 当前任务分类规则：单人 Workspace 自动拥有唯一的个人起步分类，用户可以立即创建任务；
  第二名成员正式加入后，该分类只读且只能迁出，不能新建或迁入任务。双人阶段新分类名称最多
  5 个字符，必须在“我的 → 分类管理”发起 `CLASSIFICATION_CREATE` 双人审批后使用。
  协议字段暂保留 `labels: [分类名]`，仅用于兼容快照和增量同步。

- 任务审批只有“我的”页 AppBar 的审批中心入口；清单、四象限和日程的“更多”菜单不包含任务审批；扫码登录 Web 与审批中心并列放在该 AppBar。
- 每次短信验证码校验成功都会创建或恢复一个 `ACTIVE` Android 设备，并立即授予可读写能力；首版不创建设备审批请求。设备管理只能撤销同一账号下的其他设备，撤销前必须二次确认，当前设备不可撤销。
- 个人资料只支持编辑 `display_name`；首尾空格清理、空值和最大长度由服务端统一处理。手机号和头像不可编辑，客户端继续使用默认 `CircleAvatar`。
- Workspace bootstrap 返回 ACTIVE 成员的 `match_status`、数量、名称、脱敏手机号和 `is_current`：零或一名成员为 `waiting_partner`，两名成员为 `matched`。未匹配时客户端显示默认头像和“匹配中”，不显示虚假的对方身份；匹配后才显示另一位 ACTIVE 成员。
- 设备签名挑战和任务化设备审批保留为未来安全增强，不属于当前运行路径，详见[延期的设备验证审批设计说明](./superpowers/superseded/2026-09-02-device-approval-task-design-note.md)。

当前补充的验收重点：首次和后续短信登录设备均可写；遗留未撤销设备迁移后可写；清单菜单无审批；“我的”页能进入审批中心、Web 扫码和设备管理；名称编辑与匹配占位状态在 API 和客户端 fixture 中保持稳定。

## 历史路线（仅作记录）

以下 Phase 0-9 记录旧的分阶段路线，仅用于追溯，不覆盖上面的当前账户、设备和匹配边界。

## 发布分层

本项目不把所有功能一次性视为同一个 MVP：

- `MVP-Core`：Phase 0-3，先跑通两人任务闭环和完整行为记录；
- `MVP-Extended`：Phase 4-7，补充冲突、事件、循环任务、评论和首页；
- `Post-MVP`：Phase 8-9，在真实使用数据基础上做统计和反拖延优化。

只有 `MVP-Core` 完成后，才进入下一层。任何新增功能都不能阻塞核心闭环。

## Phase 0：工程基础

目标：跑通完整部署链路。

- Git 仓库；
- Flutter Android/Web 工程；
- Go API；
- PostgreSQL；
- Docker Compose；
- Caddy；
- Migration；
- HTTPS；
- CI/CD 基础流程。

验收：

- Android 能登录 API；
- Web 能登录 API；
- API 能连接 PostgreSQL；
- 数据库能完成初始化和迁移；
- ECS 能通过 HTTPS 访问。

## Phase 1：双人系统

- 手机号用户注册与登录；
- Android 短信验证码登录；
- Access/Refresh Token；
- `display_name` 修改；
- 默认头像；
- 获取双方用户信息；
- 基础会话撤销。

验收：

- 两台 Android 设备可以分别以两个手机号用户登录；
- 双方看到统一数据；
- 名称修改后双方可刷新看到；
- 头像不可修改。

## Phase 2：Task 和子任务

- 创建、查看、编辑、取消任务；
- 每项任务只有一个 `current_handler_id`；
- 同一 Workspace 的两位 ACTIVE 成员可读取全部未删除任务和子任务；
- 当前负责人可直接写入，另一位成员的受保护写入继续走对方审批；
- 用户独立任务排序；
- 转交负责人；
- 开始、完成、重开；
- 一层子任务；
- 计划开始时间；
- 截止时间；
- 预计耗时。

验收：

```text
创建
  -> 确定当前负责人（默认是创建者）
  -> 开始
  -> 转交
  -> 完成
  -> 双方刷新看到同一状态；非负责人写入须经对方审批
```

## Phase 3：延期和阻塞

- DelayRecord；
- 延期原因必填；
- `OTHER` 补充说明；
- 延期次数和累计延期时间；
- `BLOCKED` 状态；
- `REVIEW` 状态；
- 阻塞原因必填；
- 解除阻塞后的继续处理人；
- 状态历史；
- 负责人历史；
- 统一 ActivityEvent。

验收：

- 一个任务延期三次后可以查看三次完整记录；
- 每次延期保留原截止时间和新截止时间；
- 进入阻塞时必须说明原因和后续负责人；
- 解除阻塞后自动恢复到正确处理人。

## Phase 4：状态冲突

- `status_version`；
- 过期版本返回 409；
- 创建冲突记录；
- 冲突专区；
- 双方确认最终状态；
- 冲突解决事件；
- 旧冲突被新状态提交替代时标记 `SUPERSEDED`。

验收：

- 两台设备同时修改同一任务状态时不发生静默覆盖；
- 冲突不影响其他任务和普通字段；
- 双方确认相同结果后任务才合并；
- 所有状态尝试和解决过程可审计。

## Phase 5：重要事件

- 一次性事件；
- 日期型事件；
- 具体时间事件；
- 年度纪念日；
- 北京时间倒计时；
- 时间轴；
- 软删除。

验收：

- 可以创建婚礼、旅行、预约和纪念日；
- 正确显示还有多少天或已过去多少天；
- 纪念日自动计算下一次发生日期。

## Phase 6：循环任务

- 每日；
- 每周；
- 每月；
- 暂停和恢复；
- Task Instance；
- 幂等生成；
- 错过周期不补历史任务；
- 月末日期处理。

验收：

```text
RecurringTask
    -> 到期
    -> Task Instance
    -> 完成
    -> 计算下一次 occurrence
```

## Phase 7：协作和首页

- 评论；
- 任务时间线；
- 首页 `/api/v1/home`；
- 当前处理任务；
- 用户自定义顺序；
- 当前阻塞任务；
- 待我验收任务；
- 到期提醒；
- 重要事件倒计时；
- 未处理冲突数量。
- Android“我的”账户概览：统计当前用户负责的全部未删除父任务和子任务，并汇总完成、未完成和延期数据；匹配对象头像打开对方的同口径概览。

首页默认展示用户排序中的前 5 条开放任务，不显示系统优先级。

## Phase 8：数据分析

第一批指标：

- 到期任务数；
- 完成任务数；
- 延期任务数；
- 延期次数；
- 累计延期时间；
- 平均延期时间；
- 中位延期时间；
- 重复拖延率；
- 平均启动延迟；
- 共同任务拖延率。

第一版统计实时计算，不保存汇总缓存。

Android“我的”中的账户概览是从现有 Workspace snapshot 派生的紧凑视图，不属于独立的数据分析子系统；不新增 analytics API、统计表或统计缓存。

## Phase 9：反拖延优化

根据真实使用数据优化：

- 首页展示数量；
- 任务拆分体验；
- 阻塞原因分类；
- 重复延期提示；
- 等待对方识别；
- 时间段行为分析；
- 自动拆分建议。

AI 放在这一阶段，不进入 MVP。

## 最终验收原则

每个产品功能都应回答：

1. 是否帮助用户更快开始？
2. 是否帮助两个人更好协作？
3. 是否减少任务过载？
4. 是否记录真实行为？
5. 是否能够发现拖延模式？

如果不能回答这些问题，不因为“看起来很酷”而进入 MVP。
