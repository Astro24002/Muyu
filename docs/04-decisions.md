# 已确认设计决策

本文记录讨论中已经确认的设计。当前运行时规则以 [云端协调双人协作架构设计](./superpowers/specs/2026-08-24-cloud-coordinated-collaboration-design.md) 为准；本文件后半部分的 P2P 与旧 Phase 0-3 决策仅作历史记录，不能作为新实现依据。

## 当前云端协调架构（2026-08-24）

- PostgreSQL 是 Workspace、成员、设备、任务、评论、延期、活动、冲突和同步 cursor 的唯一事实源，任务内容可以明文保存；
- 后端采用 FastAPI 模块化单体；REST 负责读取、写入和增量同步，WebSocket 只在事务提交后通知变更；
- 首版只交付 Android 和 Web。Android 产出 APK/AAB，Web 产出静态构建，二者必须连接同一 API、权限和同步协议并完成互操作验收；iOS 暂不实现；
- 用户由手机号唯一标识，Android 仅用短信验证码登录；每个用户首版最多一个 ACTIVE Workspace，每个 Workspace 最多两名权限对等成员；
- 新增长期 Android 设备必须由另一成员的 ACTIVE Android 设备经安全短码批准；浏览器仅能由当前用户自己的 ACTIVE Android 设备扫码授权，最长 18 小时，并可由该用户任一 ACTIVE Android 设备撤销；
- 客户端不允许离线提交。服务端 ACK 才是提交成功；cursor 增量读取、30 秒兜底轮询、回前台与手动刷新共同恢复同步；
- 同字段与生命周期并发返回可审计的 409 冲突，不同字段自动合并；删除为软删除，操作、评论、延期和活动历史追加保存；
- 任务分类是 Workspace 级已批准资源；每项新任务必须且只能选择一个分类。协议字段
  继续使用 `labels` 数组兼容既有同步，但新写入只接受一个值。Workspace 不创建系统
  “默认”分类；首个及后续分类仅能在“我的 → 分类管理”发起，必须经另一位成员的
  `CLASSIFICATION_CREATE` 审批后才能使用。在首个分类获批前不得创建任务；
- 首版搜索使用 PostgreSQL 全文检索、GIN 与 pg_trgm，不引入 Elasticsearch/OpenSearch。未来搜索索引只能是可重建读投影，永远不是事实源；
- 新架构从空数据库和空 Workspace 开始，后续实施会删除旧 P2P 与旧固定密码后端运行时，不迁移旧数据，也不保留兼容 API。

## 历史决策（不再生效）

### Local-first P2P 架构（2026-08-21）

- 新任务事实只存在于两台 Android 客户端的本地 Event Store；
- P2P 是唯一同步方式，首版使用二维码/短码接触匹配和局域网或设备热点传输；
- ECS、公有云中继、云端备份和云端恢复不进入首版；
- 一个工作区只有 A、B 两个成员槽位，每位成员同时只有一台活动设备；
- 换机由另一方现有可信设备批准，新设备生成全新的设备密钥并替换原成员槽位；
- 设备签名密钥和密钥交换密钥分离，私钥由 Android Keystore 保护；
- 事件使用每事件 DEK 加密，DEK 由 Epoch Key 封装，Epoch Key 分别封装给两台活动设备；
- 每台设备维护独立 hash 链，事件用因果上下文判断先后或并发，不使用全局单链；
- 延期、评论、删除和活动记录追加事件；物化任务状态可以从事件重建；
- 并发状态不使用最后写入覆盖；冲突保持 OPEN，暂时禁止该任务后续状态操作，双方确认完整目标状态后生成 ConflictResolved；
- 传输断线、重复、篡改和投影损坏分别通过断点续传、event_id 幂等、隔离事件和事件重放处理；
- 两台设备都丢失时，当前版本不提供历史恢复，旧工作区数据不可恢复；
- 新 P2P 首版从新建工作区开始，现有 PostgreSQL 任务数据不自动迁移。

### 用户和认证

- 系统固定两名用户；
- 手机号是固定用户 ID 和登录名；
- 两人使用同一套固定密码；
- 密码通过部署 Secret 注入，数据库只保存哈希；
- 不开放注册；
- MVP 不提供改密码；
- 头像固定；
- 昵称和角色可以修改；
- 角色只用于展示，不参与业务权限判断。

### 任务和负责人

- 任务参与人可以是一人或两人；
- 当前实际负责人独立于参与人；
- MVP 始终只有一个当前负责人；
- 负责人可以频繁转交；
- 转交必须写入负责人历史和活动事件；
- 子任务使用同一套任务模型；
- 第一版只支持一层子任务；
- 父子任务状态相互独立。

### 状态和阻塞

- 状态为 `TODO`、`IN_PROGRESS`、`WAITING`、`DONE`、`CANCELLED`；
- `WAITING` 必须填写阻塞原因；
- `WAITING` 必须指定解除后继续处理人；
- 解除阻塞后自动进入 `IN_PROGRESS`；
- `DONE` 和 `CANCELLED` 可以恢复；
- 所有状态变化必须保存历史。

### 延期

- 延期原因必填；
- `OTHER` 必须填写说明；
- 每次延期生成不可修改的 `DelayRecord`；
- 禁止直接覆盖延期历史；
- 延期、任务更新和活动记录在同一事务中完成。

### 排序和首页

- 系统不保存任务优先级和紧急程度；
- 每个用户维护自己的任务展示顺序；
- 用户排序不产生冲突；
- 首页只展示少量任务；
- 首页顺序遵循用户自己的排序；
- 时间提醒按时间排序，不代表业务优先级；
- 首页默认展示前 5 条开放任务。

### 冲突

- 只有任务状态并发修改产生冲突；
- 冲突不是任务状态；
- 冲突不锁定任务、不影响全局；
- 双方可通过其他沟通途径协商；
- 双方确认相同最终状态后合并；
- 新状态提交可以使旧冲突标记为 `SUPERSEDED`；
- 冲突创建、确认和解决全部进入活动记录。

### 时间和循环规则

- 业务时区固定为 `Asia/Shanghai`；
- 数据库存储绝对时间时使用 UTC；
- 纪念日按年度重复事件处理；
- 倒计时不持久化；
- 循环任务支持每日、每周、每月；
- 不无限预生成未来实例；
- 错过多个周期不补历史实例；
- 每月 31 日在目标月份不存在时使用当月最后一天；
- 通过唯一约束保证循环实例幂等。

### 审计和沟通

- 所有任务和子任务变更都写入追加式事件表；
- 活动记录不可修改和删除；
- 评论 MVP 只支持新增和查看；
- 暂不使用 WebSocket、Push 或消息队列；
- 未处理冲突通过接口和页面提示，不依赖实时推送。

### 工程与镜像

- 后端使用 Python 3.12；
- Docker 基础镜像统一使用 `m.daocloud.io/docker.io` 镜像源；
- 当前使用 `m.daocloud.io/docker.io/library/python:3.12-slim` 和 `m.daocloud.io/docker.io/library/postgres:16-alpine`；
- 镜像源变更必须同步更新 Dockerfile、Compose、实施计划和开发状态记录。

### 设计边界

不进入 MVP：

- 多租户；
- Workspace、Team、Organization；
- RBAC；
- OAuth；
- 微服务；
- Redis、MQ、Elasticsearch；
- AI 自动规划；
- 排行榜、积分和惩罚机制。
