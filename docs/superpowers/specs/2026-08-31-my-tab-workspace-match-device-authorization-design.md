# “我的”页双人匹配与设备授权设计

## 1. 背景与目标

Muyu 是一个只允许两位用户共同使用的共享空间。账号匹配关系与设备授权是两个不同层级的概念：

- 账号匹配关系决定哪两位用户属于同一个 workspace。
- 设备授权关系决定某个账号下的设备是否拥有写权限。

当前后端已有 workspace membership、Android device 和 device authorization request 模型，但 Android “我的”页没有把这些信息组合成完整的用户流程。新设备登录后可能处于未验证状态，但不应阻塞共享空间加载；另一位用户应能在“我的”页看到并处理设备验证请求。

本设计的目标是：

1. 在“我的”页清晰展示两位用户的共享空间匹配关系。
2. 展示当前账号的设备状态和读写权限。
3. 为新设备提供自动发起、可追踪的验证请求流程。
4. 为另一位已验证用户提供审批入口。
5. 保持双人 workspace、不可自撤销当前设备、Web 临时会话不计入永久设备列表等既有约束。

## 2. 约束与非目标

### 约束

- 一个 workspace 永远最多两个有效 membership。
- 一个账号可以拥有多个 Android 设备。
- 账号的第一台设备默认 `已验证`；后续设备默认 `未验证`。
- 未验证设备可以读取数据，但不能执行写操作。
- 新增长期 Android 设备必须经过另一位用户的已验证设备批准。
- 当前设备不能撤销或删除自己。
- Web 登录是短期、可撤销的临时 session，不创建永久 Android device，也不进入设备验证列表。
- 同一 workspace 内可以展示另一位用户的脱敏身份信息，但不能跨 workspace 查询信息。

### 非目标

- 首版不增加群组、管理员、多方投票或跨 workspace 审批。
- 首版不引入 WebSocket 或复杂实时通知系统。
- 首版不提供主动解除双人 workspace 绑定的常规入口。
- 首版不把完整手机号、设备公钥或任何私钥暴露给客户端展示层。

## 3. 方案选择

### 方案 A：只展示账号匹配关系

“我的”页只显示两位用户和 workspace 状态，设备验证仍由独立页面或隐藏入口处理。

优点是改动最小；缺点是无法解决当前“新设备等待验证但用户不知道下一步做什么”的问题，审批流程仍不可发现。

### 方案 B：账号匹配与设备授权分区展示（推荐）

“我的”页上半部分展示双人匹配关系，下半部分展示当前账号设备、发起的请求和待处理请求。设备验证操作从这里进入现有审批页面。

该方案保持现有领域模型，只补齐数据投影、请求编排和入口，能够覆盖实际问题而不过度扩大产品复杂度。

### 方案 C：单一关系图展示账号、设备和 Web session

把两位用户、所有设备和 Web session 放在一张关系图中。

该方案视觉表达复杂，容易把临时 Web session 误认为永久设备，也会扩大权限和数据投影范围，不适合作为轻量级首版。

最终采用方案 B。

## 4. Android “我的”页设计

页面按以下顺序展示。

### 4.1 当前账号信息

展示当前用户的显示名称、用户 UUID、脱敏手机号、当前设备名称、设备状态和权限。

示例：

```text
我的账号
显示名称：我
手机号：+86 150****8726
当前设备：Pixel 8
状态：已验证
权限：可读写
```

用户 UUID 可用于诊断和客服支持，但不作为主要身份文案。

### 4.2 共享空间匹配卡片

卡片标题为“共享空间”，显示 workspace 名称、成员数量和匹配状态，并列出两位成员：当前用户标记为“我”，另一位用户标记为“对方”。手机号默认脱敏。

匹配状态：

| `match_status` | 判定 | 页面文案 |
| --- | --- | --- |
| `waiting_partner` | 有效 membership 少于 2 个 | 等待对方加入 |
| `matched` | 两个 membership 均为 `active` | 已匹配 · 2/2 位成员 |
| `error` | 数据不完整、重复或状态矛盾 | 匹配异常 |

“匹配异常”只提供刷新和错误详情，不允许客户端自行修复 membership。

首版不提供解除绑定按钮，避免误触导致双人关系破坏。

### 4.3 设备卡片

设备卡片只列出当前账号的设备：

- 当前设备：显示“当前设备”，不可删除、不可撤销。
- 其他已验证设备：显示“已验证 · 可读写”，可以撤销。
- 未验证设备：显示“未验证 · 只读”，显示等待对方验证的请求状态。
- 已撤销设备：默认折叠，仍保留审计信息。

设备状态只允许以下值：

```text
未验证 -> 已验证 -> 已撤销
未验证 -> 已撤销
```

### 4.4 设备验证请求

请求分为两个列表，避免用户无法判断自己需要等待还是需要操作。

#### 我发起的请求

显示候选设备名称、创建时间、过期时间和当前状态：

- `pending`：等待另一位用户验证
- `approved`：验证完成
- `rejected`：被拒绝
- `expired`：已过期
- `cancelled`：已取消

#### 待我处理的请求

显示另一位用户账号的脱敏信息、候选设备名称、平台和请求有效期，提供“验证设备”和“拒绝”操作。

验证操作继续复用现有的 begin-approval/signature/approve 流程，页面只负责展示和导航。

## 5. 业务流程

### 5.1 首次登录

1. 用户完成验证码登录。
2. 如果该账号没有设备，创建第一台 Android device 并标记为 `active`。
3. 如果 workspace 只有一位成员，页面显示“等待对方加入”；如果已有两位成员，页面显示“已匹配”。
4. 不创建设备验证请求。

### 5.2 新设备加入

1. 新 Android 设备完成登录。
2. 后端创建该设备并标记为 `pending`。
3. 移动端完成基础会话初始化后，自动创建一条设备授权请求。
4. 创建请求必须幂等：同一 pending device 存在有效请求时直接返回现有请求，不能重复创建。
5. 新设备进入共享空间后保持只读，不因 `pending` 状态阻塞 bootstrap、任务读取或“我的”页加载。
6. “我的”页显示“等待另一位用户验证”。

### 5.3 另一位用户批准

1. 已验证设备加载“我的”页时获取待处理请求。
2. 用户点击“验证设备”。
3. 客户端获取挑战并使用本地设备私钥签名。
4. 后端验证请求未过期、候选设备属于另一位 workspace 成员、审批设备为 active、签名有效且请求未使用。
5. 审批成功后候选 device 和对应 membership 均转为 `active`。
6. 新设备下次刷新或恢复页面时获得写权限。

## 6. 后端数据投影与接口

建议扩展现有 workspace bootstrap 响应，避免首版增加过多聚合接口：

```json
{
  "workspace": {
    "id": "workspace-id",
    "name": "共享空间",
    "match_status": "matched",
    "member_count": 2,
    "members": [
      {
        "user_id": "user-a",
        "display_name": "我",
        "phone_masked": "+86 150****8726",
        "membership_status": "active"
      },
      {
        "user_id": "user-b",
        "display_name": "对方",
        "phone_masked": "+86 150****0169",
        "membership_status": "active"
      }
    ]
  },
  "devices": {
    "mine": [],
    "incoming_requests": [],
    "outgoing_requests": []
  }
}
```

接口规则：

- 只允许 workspace 成员读取上述成员投影。
- 成员投影只返回展示所需的脱敏字段，不返回设备私钥、公钥或 OTP 信息。
- 设备列表默认只返回当前用户设备；对方设备通过待处理请求以最小字段展示。
- `POST /devices/authorization-requests` 对同一 pending device 做幂等处理。
- 请求列表返回请求 ID、候选设备标签、候选用户脱敏信息、状态、创建时间和过期时间。
- 安全码只在创建请求的设备上显示并由客户端安全保存；服务端只保留摘要，不在普通列表接口返回明文安全码。
- 审批接口必须再次校验“审批者”和“候选设备所属用户”是同一 workspace 中的两位不同用户。

## 7. 刷新与错误处理

“我的”页进入时加载一次 workspace、设备和授权请求数据；下拉刷新时统一重新加载。应用从后台恢复且距离上次加载超过设定时间时再次刷新。首版不引入 WebSocket。

错误处理：

- `401`：刷新会话或回到登录流程。
- `403`：保留页面读取能力，仅提示当前设备为只读。
- `409`：使用服务端返回的已有请求，避免创建重复请求。
- `410`：提示请求已过期，并允许新设备重新发起请求。
- 网络错误：保留上次缓存，显示可重试状态，不清空已有匹配关系。

## 8. 验收标准

### Android

- “我的”页能显示当前用户和另一位用户的匹配关系。
- 只有一位成员时显示“等待对方加入”，不会显示“无法加载共享空间”。
- 新设备显示“未验证 · 只读”，并能看到发起请求的状态。
- 已验证用户能在“我的”页看到待处理设备验证请求并进入审批。
- 审批成功后新设备变为“已验证 · 可读写”。
- 当前设备没有删除或撤销自己的操作。
- Web 临时登录不会出现在永久设备列表和设备撤销列表中。
- 下拉刷新能同步匹配关系、设备状态和请求状态。

### FastAPI 与数据库

- workspace bootstrap 返回双人成员最小展示投影。
- 跨 workspace 访问被拒绝。
- 设备验证请求创建具备幂等性。
- 请求状态只能按定义的状态机迁移。
- 只有另一位用户的已验证设备可以批准请求。
- 现有只读权限和“不能撤销当前设备”测试继续通过。

## 9. 后续实施拆分

实施时按以下顺序执行：

1. 后端补充 workspace 成员投影和请求聚合响应。
2. 后端实现设备验证请求幂等与双人授权校验。
3. Android 增加“我的”页匹配卡片、设备状态和请求卡片。
4. 接通新设备自动发起请求和审批页面入口。
5. 增加后端单元/API 测试与 Android 页面/流程测试。
6. 在本地构建带 commit ID 的 debug APK，完成验证后再按版本流程发布。
