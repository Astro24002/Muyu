# Muyu 轻量行动协作规格

## 1. 目的与定位

Muyu 是一个最多两人使用的私人行动协作系统。它帮助双方明确下一步、记录负责人、看见截止时间、保留延期和阻塞事实，而不是成为 Jira、Asana、Worktile 或 Teambition 的通用替代品。

本规格选择“行动优先版”，并明确以低复杂度为第一约束。新增能力必须优先复用现有 Workspace、Task、状态历史、评论、延期、冲突和 cursor 同步模型。

## 2. 当前版本范围

### 2.1 保留并完善

- 一个 Workspace，最多两名成员；
- Task 和一层 Subtask；
- 标题、描述、当前处理人、参与人、截止时间、计划开始时间和预计耗时；
- 固定状态：`TODO`、`IN_PROGRESS`、`WAITING`、`DONE`、`CANCELLED`；
- 手动阻塞原因、解除后处理人和追加式延期记录；
- 评论、活动历史、字段版本和 409 冲突处理；
- 当前用户的“我的任务”视图；
- 列表视图和按状态分组的简单看板视图；
- 基于截止时间、状态和延期记录的基础提醒与统计；
- Android 与 Web 通过现有 FastAPI、PostgreSQL、cursor 和 WebSocket 通知保持一致。

### 2.2 轻量化决定

- 不新增 `Project`、`Team`、`Portfolio`、`Version`、`Sprint` 或 `Cycle` 数据层级；
- 不开放自定义状态或工作流编辑器，状态转换沿用固定规则；
- 不实现 Scrum、燃尽图、控制图、资源负载和高级报表；
- 不实现任务依赖图。任务间等待关系继续使用现有 `WAITING`、阻塞原因和人工说明表达；
- 不在本阶段加入对象存储、附件上传或文件预览；
- 不增加自定义字段、自动化、OKR、知识库、审批和插件机制；
- 不增加离线写入、本地事实源或第二套客户端缓存模型。

个人任务顺序、截止时间和阻塞事实承担轻量优先级作用。本阶段不增加独立的业务优先级评分，避免系统替用户做判断。

## 3. 交互原则

首页首先展示当前用户正在处理的少量任务、阻塞任务、临近截止任务和未处理冲突。完整列表可以进入，但不作为默认压力指标。

看板列是 `Task.status` 的投影，不保存独立的看板状态。列表、看板和提醒都读取同一份服务端任务快照。

创建任务只要求标题；描述、负责人、截止时间和子任务可以随后补充。状态变化、转交、延期、阻塞、评论和恢复都应保留活动记录。

## 4. 数据与同步约束

不为本规格新建事实源。所有写入继续在一个 PostgreSQL 事务中完成：权限校验、幂等检查、当前状态更新、字段版本、操作记录、活动记录和 Workspace cursor。

WebSocket 只通知“可能有变化”；客户端收到通知后通过现有 snapshot/changes API 刷新。网络不可用时只允许查看可能过期的数据，不允许排队提交。

删除继续采用软删除。任务历史、评论、延期和活动记录不可由用户物理删除。

## 5. 未来候选，不属于当前版本

以下能力保留为候选，不提前在数据库或 API 中预留复杂抽象：

1. 单一完成前置依赖；
2. 轻量 Project/Area 分组；
3. 日历和简单时间线；
4. 附件元数据与对象存储；
5. 固定优先级枚举；
6. 基于状态历史的周期统计。

只有真实使用证明当前模型不足时，才为候选能力增加独立表或新的权限边界。

## 6. 验收标准

- 新用户无需配置项目、团队或工作流即可创建和推进任务；
- 两名成员在 Android 和 Web 看到相同的任务状态、评论、延期和冲突；
- 看板、列表和首页不会产生互相矛盾的状态；
- 任务延期和阻塞原因可追溯，历史不会被覆盖；
- 断网不会产生伪造的成功写入或隐藏的离线队列；
- 本阶段不增加新的必需基础设施、外部服务或组织权限模型；
- Android APK/AAB、Vite Web 静态包和现有后端验收边界保持不变。
