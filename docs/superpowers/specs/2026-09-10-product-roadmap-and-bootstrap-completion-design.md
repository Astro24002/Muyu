# Muyu 产品路线与单人起步、双人验收设计

## 1. 文档目的

本文将产品路线收敛为一条可验证的使用路径，并补充单人起步阶段与双人任务验收的规则。
本文属于产品和领域设计，不启动工程施工。后续实施计划必须以本文和现有云端协作规格为依据。

## 2. 产品目标

Muyu 服务固定两个人的私人行动协作。产品首先解决四个问题：

1. 一个人可以立即记录和推进自己的事情；
2. 另一人加入后，双方看到同一份任务事实；
3. 任务由负责人提交结果，由另一人确认后才算完成；
4. 延期、阻塞、退回和审批过程能够被回看。

产品不扩展为通用项目管理平台，不引入第三位成员、复杂角色、公开分享、积分排名或自动规划。

## 3. 生命周期

### 3.1 单人起步阶段

Workspace 只有一名 ACTIVE 成员时：

- 后端为 Workspace 自动提供唯一的个人起步分类；
- 起步分类的显示名称取当前用户的 `display_name`，但分类记录必须使用稳定的系统标识和 `bootstrap` 标记，不能通过名称判断；
- 分类可以不出现在普通分类选择器中；新任务由服务端自动关联该分类；
- 用户可以创建任务、编辑任务、推进、阻塞、延期、评论和创建一层子任务；
- 新任务负责人只能是当前用户；
- 任务不能直接进入 `DONE`；
- 另一位成员尚未加入时，不能创建有效的验收审批。完成操作应显示“等待另一位成员加入后提交验收”，任务保持 `IN_PROGRESS`；
- 起步分类最多只有一个，不能通过多设备、刷新或重复请求创建第二个。

起步分类是系统为保证单人可用而提供的内部资源，不等同于用户主动创建的共享分类。

### 3.2 双人协作阶段

第二名用户正式成为 Workspace 的第二名 ACTIVE 成员后，Workspace 进入 `matched`：

- 起步分类变为只读迁移分类；
- 起步分类仍可在历史、筛选和任务详情中显示，并明确标记“已停用”；
- 起步分类下已有任务可以继续编辑、评论、延期、阻塞和推进；
- 不能在起步分类中新建任务，也不能把其他任务迁入起步分类；
- 新任务必须选择已批准的共享分类；
- 新共享分类必须由一方发起 `CLASSIFICATION_CREATE`，另一方批准后才可使用；
- 起步分类下的任务迁移到共享分类时保留任务编号、父子关系、评论、延期和活动历史；
- 负责人可以直接迁移自己的任务，另一人迁移时继续遵守负责人审批规则。

加入状态以服务端 ACTIVE 成员数量为准。填写手机号、发出邀请或登录验证码成功但尚未成为 Workspace 成员，都不触发阶段切换。

## 4. 任务完成与验收

### 4.1 状态规则

任务状态继续使用：

```text
TODO -> IN_PROGRESS -> REVIEW -> DONE
                         \-> IN_PROGRESS
```

`BLOCKED` 和 `CANCELLED` 仍按现有状态机执行；阻塞解除回到 `IN_PROGRESS`。

### 4.2 提交验收

双人阶段，任务负责人不能直接把任务改为 `DONE`。负责人只能执行“提交验收”：

- 任务从 `IN_PROGRESS` 进入 `REVIEW`；
- 服务端在同一事务中创建一条任务验收审批；
- 审批人固定为另一位 ACTIVE 成员；
- 负责人不能审批自己的验收请求；
- 同一任务同时只能有一条待处理的验收请求；重复提交必须幂等。

`REVIEW` 任务在清单中作为待处理动作展示，不再作为普通进行中任务展示。

### 4.3 审批结果

另一位成员批准时：

- 审批请求变为 `APPROVED`；
- 任务变为 `DONE`；
- 写入完成时间和活动事件。

另一位成员驳回时：

- 必须填写驳回原因；
- 审批请求变为 `REJECTED`；
- 任务回到 `IN_PROGRESS`；
- 保存驳回原因、审批人和时间；
- 负责人修改后可以再次提交新的验收请求，旧请求仍保留在审批记录中。

审批请求和任务状态必须在一个数据库事务中更新。任何一方失败都不能留下“审批已通过但任务仍待验收”或“任务已完成但审批未完成”的中间状态。

## 5. 产品路线

### R0：激活和单人可用

目标是让第一位用户登录后立刻能够记录事情。

- 自动提供个人起步分类；
- 没有分类审批时允许创建个人任务；
- 单人任务负责人固定为当前用户；
- 清楚提示任务无法在单人阶段完成；
- 首次创建后可以从清单、详情和日程找到任务。

验收：首次登录用户不需要等待第二人或分类审批即可创建任务；重复请求不会创建重复分类或重复任务。

### R1：双人加入和共享分类

目标是让第二位用户加入后，系统从个人记录切换到共同协作。

- 匹配状态从 `waiting_partner` 变为 `matched`；
- 起步分类只读并支持迁出；
- 共享分类申请、审批、展示和任务选择闭环；
- 双方可以读取同一 Workspace 的任务和历史。

验收：起步分类下的旧任务可继续推进，但新任务只能选择已批准的共享分类。

### R2：双人验收闭环

目标是让“完成”成为双方共同确认的事实。

- 负责人提交 `REVIEW`；
- 另一人从审批中心看到验收请求；
- 批准进入 `DONE`；
- 驳回回到 `IN_PROGRESS` 并记录原因；
- Android、Web、API、同步和活动历史使用同一状态契约。

验收：负责人无法绕过审批写入 `DONE`；审批结果刷新后两台设备状态一致。

### R3：同步和可靠性

目标是让双方及时看到变化并能恢复异常。

- Android 接入 Workspace 变更通知；
- 回到前台刷新；
- 受控兜底轮询；
- 手动下拉刷新；
- 延期、分类迁移等所有写操作执行与负责人审批一致的权限校验；
- 统一错误、重试和过期游标恢复。

验收：一台设备修改后，另一台设备在通知或兜底周期内看到变更；网络失败不会显示虚假的成功状态。

### R4：任务可发现性

目标是让任务不会因为行动窗口而“消失”。

- 清单继续保持“逾期、阻塞、即将到期”的行动视图；
- 增加明确的全部任务和历史入口；
- Android 增加“待我验收”入口；
- 分类筛选应用于清单各分组；
- 父任务、子任务和任务历史提供稳定导航。

验收：七天行动窗口之外的任务仍可被用户主动找到；待验收任务无需依赖猜测或搜索才能处理。

### R5：提醒和重复行为

只有 R0-R4 在真实使用中稳定后，才评估：

- 到期提醒和待验收提醒；
- 每日、每周、每月重复任务实例；
- 重要日期与年度纪念日。

提醒必须支持关闭和去重；重复任务不能生成无限未来实例。统计、AI 规划、复杂报表、多人 Workspace 和 iOS 不属于这条路线的近期目标。

## 6. 实施门禁

每个路线阶段必须先完成产品契约和失败场景，再进入代码施工。最低验证范围包括：

- 单人 Workspace 与双人 Workspace 的权限差异；
- 任务状态转换和审批幂等；
- 第二位成员加入时的起步分类迁移规则；
- 快照、增量同步和缓存的一致性；
- Android 与 Web 显示中文状态且使用相同内部枚举；
- PostgreSQL 新库迁移和线上健康检查。

在 R2 完成前，不增加新的任务状态；在 R3 完成前，不把实时通知当作唯一同步路径；在 R4 完成前，不继续扩大首页功能范围。
