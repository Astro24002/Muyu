# 双人协作行动管理系统

> 任务模型、Workspace 读取范围、负责人写入与双人审批、Android“我的”概览、迁移和缓存规则以 [移除任务参与人模型设计](./superpowers/specs/2026-09-01-remove-task-participants-design.md) 为当前权威；身份、设备、云端同步与 Web 授权仍以 [云端协调双人协作架构设计](./superpowers/specs/2026-08-24-cloud-coordinated-collaboration-design.md) 为准；Android“我的”页、设备和资料边界以 [我的页审批、设备管理与用户资料设计](./superpowers/specs/2026-09-02-my-tab-approval-device-profile-design.md) 为准。本文件描述产品目标与任务行为，不再定义旧的固定账号或共享密码模型。

## 1. 产品定义

这是一个只服务于两个人的私人行动记录与提醒应用。

它不追求成为通用 Todo、团队协作平台或复杂的数据分析系统，而是解决两个人日常生活中的几个具体问题：

- 现在正在处理什么；
- 下一步由谁继续；
- 什么事情被阻塞了，为什么；
- 截止时间是否发生过延期；
- 重要日期什么时候到来；
- 任务和子任务经历过哪些变化。

产品核心价值：

> 让两个人更容易开始行动，也让事情的真实过程不会丢失。

## 2. 产品边界

这是一个小而精的私人应用程序。

系统只服务于一个最多两名成员共同使用的私人 Workspace，不提供以下平台化能力：

- 第三位成员；
- 多 Workspace 切换、Team、Organization；
- 多租户；
- RBAC 和复杂权限；
- 公开分享；
- 社交关系；
- 排行榜、积分和惩罚；
- AI 自动规划；
- 面向用户的即时聊天或复杂实时通信。

所有设计优先考虑：少配置、少页面、少打扰、低维护成本。

## 3. 用户模型

用户由手机号唯一标识。首版用户在 Android 上通过短信验证码注册或登录，不使用共享密码或启动时预置账号。

用户 A 在自己的 Android 设备创建 Workspace，并按手机号邀请用户 B；B 完成短信验证并接受邀请后加入。一个 Workspace 最多有两名 ACTIVE 成员，权限完全对等；一个用户在首版最多属于一个 ACTIVE Workspace。

每次短信验证成功都会让当前 Android 登录设备成为 `ACTIVE` 且可读写，不创建设备审批请求，也不要求另一位成员确认。用户只能在自己的账号内撤销其他设备，当前设备不能撤销；Web 只能由当前用户自己的活动 Android 设备扫码登录，浏览器会话最长 18 小时。当前交付 Android 与 Web；iOS 只保留未来接入空间。

昵称和展示资料不参与权限判断，所有授权都以 `user_id`、Workspace 成员关系和 Device 或 WebSession 状态为准。

### 3.1 Android“我的”概览

“我的”页从现有 Workspace snapshot 派生紧凑的账户概览，不新增统计接口、统计表或统计缓存。当前用户的概览只统计所有未删除且 `current_handler_id` 等于当前用户的 Task；父任务和子任务分别计数，包含全部任务数、未完成数、已完成数、延期次数和累计延期分钟数，累计时长显示为天、小时和分钟。

匹配成功时，账户卡片显示对方头像入口。点击后展示另一位 ACTIVE 成员的同一组概览，统计口径保持一致；快照刷新后更新，刷新失败时保留上一次结果。

任务审批只从 Android “我的”页 AppBar 的审批中心进入；清单、四象限和日程的“更多”菜单不提供任务审批。相邻的 AppBar 操作提供扫码登录 Web。

### 3.2 Android 账户、设备与资料边界

- 短信验证码校验成功后，首次设备和后续设备都直接创建或恢复为 `ACTIVE`，立即拥有当前账号权限；历史未撤销的 `PENDING` 设备在策略迁移中转为 `ACTIVE`，未完成的设备授权请求过期，已撤销设备和审计历史保留。
- 设备管理只允许撤销当前账号下的其他设备。撤销前必须经过客户端二次确认，确认后关联移动会话和刷新令牌失效；当前设备没有撤销入口。
- 个人资料只允许编辑 `display_name`。服务端清理首尾空格，允许清空并统一限制长度；手机号、头像和账号归属不可编辑。页面继续使用现有默认 `CircleAvatar`，不增加头像上传或头像资源接口。
- Workspace bootstrap 的 `match_status` 只由 ACTIVE 成员数量决定：零或一名成员为 `waiting_partner`，两名成员为 `matched`。未匹配时始终显示默认占位头像和“匹配中”，不显示虚假的对方身份；匹配后才显示另一位 ACTIVE 成员的名称、脱敏手机号和概览入口。

## 4. 设计原则

### 4.1 记录事实，不替用户决策

系统不保存或计算：

- 业务优先级；
- 紧急程度；
- 重要程度；
- 系统评分；
- 双方排名；
- 自动推荐顺序。

用户可以为自己维护任务展示顺序，但这个顺序只是个人展示偏好，不是系统判断出的优先级。

### 4.2 一次只面对少量事情

首页不展示全部任务，也不强调“还有多少未完成”。

首页只展示：

- 当前用户正在处理的任务；
- 当前用户排序靠前的少量开放任务；
- 阻塞任务；
- 临近或已经到期的任务；
- 重要日期和纪念日；
- 未处理的并发冲突。

完整任务列表始终可进入，但不作为首页默认内容。

### 4.3 每个任务都要能说明下一步

任务应当足够具体，能够直接开始。

过大的目标可以拆成一层子任务，例如：

```text
准备婚礼
├── 确定酒店
├── 联系婚庆
└── 整理宾客名单
```

系统不自动拆分任务，只提供清晰的拆分记录。

### 4.4 不隐藏拖延，但不惩罚拖延

延期、阻塞和重复延期都是事实记录，不是失败标记。

系统可以提醒：

> 这个任务已经延期 3 次。

但不进行扣分、排名、羞辱或双方比较。记录的目的只是帮助双方发现任务过大、目标不清晰或等待关系不明确。

## 5. 核心对象

### 5.1 Task

Task 表示需要采取实际行动的事情。

支持：

- 标题和描述；
- 一个当前负责人 `current_handler_id`；
- 计划开始时间；
- 截止时间；
- 预计耗时；
- 开始、完成、取消和重新打开；
- 转交负责人；
- 进入阻塞和解除阻塞；
- 延期；
- 评论；
- 一层子任务。

每项任务必须且只能属于一个已批准的 Workspace 分类。分类用于整理和筛选，
不参与负责人、状态或权限判断。每个 Workspace 在创建时自动拥有无需审批的
系统分类“默认”，可立即用于新任务；其余新分类由一方在“我的 → 分类管理”发起、
另一方批准后才可选择。分类名称最多五个字符。协议字段暂保留 `labels` 数组名称，
但新数据始终只保存一个值（例如 `labels: ["工作"]`）。

### 5.2 Subtask

子任务仍然使用 Task 模型，通过 `parent_task_id` 关联父任务。

第一版只支持一层子任务。父任务和子任务状态相互独立，完成子任务不会自动完成父任务。

父任务即使仍有未完成子任务也可以完成，但界面必须提示确认，并记录该行为。

### 5.3 Event

Event 表示具有明确时间节点的事情，重点是“什么时候发生”，而不是“是否完成”。

支持：

- 重要日期；
- 婚礼、旅行、搬家；
- 生日、预约；
- 一次性事件；
- 年度纪念日。

倒计时根据事件日期或时间实时计算，不保存剩余天数。

### 5.4 RecurringTask

RecurringTask 表示需要反复执行的生活任务，例如喂猫、打扫卫生和缴费。

第一版只支持每日、每周和每月。系统最多保留一个未完成实例，错过多个周期时不补充历史积压任务。

## 6. 任务协作模型

### 6.1 当前负责人、读取与审批

- `current_handler_id` 是唯一负责人，必须是同一 Workspace 的 ACTIVE 成员；创建任务时默认使用创建者。
- 同一 Workspace 的两位 ACTIVE 成员都可以读取全部未删除任务，包括父任务和子任务；“我的任务”只匹配 `current_handler_id == 当前用户`。
- 当前负责人可以直接修改；非当前负责人的另一位成员修改受保护字段时，继续创建发给当前负责人的单人审批请求，由对方成员确认。

两个人经常交换负责人，因此转交是正常操作，不是异常流程。

### 6.2 状态

```text
TODO
IN_PROGRESS
BLOCKED
REVIEW
DONE
CANCELLED
```

状态含义：

- `TODO`：待进行，已创建但尚未开始；
- `IN_PROGRESS`：进行中，当前负责人正在处理；
- `BLOCKED`：阻塞中，当前负责人暂时无法继续；
- `REVIEW`：待验收，当前负责人已提交结果，等待另一位成员确认；
- `DONE`：已完成，验收人已确认结果；
- `CANCELLED`：已取消，任务不再需要执行。

Android 和 Web 的用户界面只展示中文名称，英文值仅作为系统内部标识。

允许从 `DONE` 或 `CANCELLED` 恢复，历史记录不会丢失。

### 6.3 阻塞

进入 `BLOCKED` 时必须填写：

- 阻塞原因；
- 解除阻塞后继续处理的用户。

可以额外说明正在等待哪一位用户。

解除阻塞后，任务恢复为 `IN_PROGRESS`，清除阻塞信息并由预先记录的用户继续处理。

任务负责人可以将 `IN_PROGRESS` 提交为 `REVIEW`。系统默认将另一位 ACTIVE 成员设为验收人；验收通过进入 `DONE`，退回必须填写原因并回到 `IN_PROGRESS`。任务负责人不能自行确认自己的 Review。

## 7. 延期记录

延期原因必须填写。每次延期都生成一条不可修改的记录，不能直接覆盖历史。

延期记录包含：

- 原截止时间；
- 新截止时间；
- 延期用户；
- 延期原因；
- 延期时长；
- 补充说明；
- 创建时间。

第一版原因枚举：

```text
NO_TIME
TOO_LARGE
NOT_WILLING
FORGOT
WAITING_PARTNER
INTERRUPTED
OTHER
```

选择 `OTHER` 时必须填写补充说明。

## 8. 并发编辑与冲突

任务编辑采用字段级乐观并发。两端同时修改不同字段时，服务端自动合并；两端修改同一字段，或并发执行状态、完成、恢复、删除等生命周期操作时，服务端保留先成功的权威状态并返回可审计的 `409` 冲突。

冲突记录保存基线值、当前值、提议值、版本和操作者。冲突不会成为任务状态，也不会锁住其他任务或未冲突字段。任一 Workspace 成员都可以保留当前值，或以最新版本重新提交提议值；解决动作会写入操作和活动历史，不要求双方共同签名。

如果任务已经软删除，普通编辑、评论和延期必须先恢复任务。

## 9. 活动记录

任务和子任务的所有变更都需要记录：

- 创建；
- 修改；
- 创建时确定当前负责人；
- 转交负责人；
- 开始；
- 进入阻塞；
- 解除阻塞；
- 延期；
- 完成；
- 取消和恢复；
- 创建子任务；
- 评论；
- 并发冲突产生和解决。

活动记录只允许新增，不允许修改或删除。它用于任务时间线、延期回顾和冲突审计。

## 10. 首页内容

首页默认展示：

1. 当前用户正在处理的任务；
2. 按当前用户顺序排列的前 5 条开放任务；
3. 阻塞任务及阻塞原因；
4. 已到期和即将到期提醒；
5. 重要事件和纪念日倒计时；
6. 未处理的并发冲突数量；
7. 最近活动。

用户排序独立保存，用户 A 的排序不会影响用户 B。时间提醒按时间排列，但不代表业务优先级。

## 11. 产品范围

### 核心闭环

第一阶段只要求跑通：

```text
用户 A 短信登录 Android
  -> 创建 Workspace 并邀请 B
  -> B 短信登录 Android、接受邀请
  -> 创建任务
  -> 确定当前负责人（默认是创建者）
  -> 开始
  -> 转交或阻塞
  -> 延期并记录原因
  -> 完成
  -> 双方看到一致状态
```

### 核心闭环之后

- 子任务；
- 评论和任务时间线；
- 重要事件和纪念日；
- 循环任务；
- 首页提醒；
- 并发冲突专区；
- 基础延期统计。

### 明确不做

- 多租户和组织体系；
- 复杂权限；
- 社交和公开分享；
- P2P、局域网同步和离线写入队列；
- 首版设备验证审批或把设备审批伪装成任务审批；
- Web 端短信验证码直接登录或浏览器长期设备身份；
- 面向用户的即时聊天和复杂实时通信；
- AI 自动规划；
- 自动任务排序；
- 排行榜、积分和惩罚机制。

## 12. 产品验收原则

每项功能都应回答：

1. 是否让用户更容易开始？
2. 是否让两个人更容易协作？
3. 是否减少一次看到的任务数量？
4. 是否保留真实行为记录？
5. 是否避免引入不必要的复杂度？

如果一个功能不能改善上述至少一项，就不进入这个私人应用的核心版本。
